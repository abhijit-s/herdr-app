# Fork changes

This fork of [herdrdev/herdr-app](https://github.com/herdrdev/herdr-app) is the Herdr build used day to day. It carries small, focused changes that each go upstream as their own pull request, and it tracks upstream by merging `upstream/master` into `master`.

This file is the inventory of what diverges. Update it in the same commit that adds, removes or upstreams a change.

## Branches

- `master`: `upstream/master` plus every change below, merged in. This is what gets built and installed.
- `feat/<slug>`, `fix/<slug>`: one change each, branched from `upstream/master` so its pull request carries nothing else.
- `FORK.md`, `scripts/fork-sync` and `mise.local.toml` (untracked) exist only on `master`.

## Setup

- Toolchains match upstream CI: Rust 1.95.0 and Zig 0.16.0, pinned per folder in `mise.local.toml` (listed in `.git/info/exclude`). Run commands through `mise exec --`.
- `just install` builds a release into `~/Applications/Herdr.app` and points `~/.local/bin/herdr-app` at it. Quit and reopen Herdr to use it. herdr-core is installed separately and is not rebuilt.
- `just notices` needs cargo-about 0.9.3: `cargo install --locked cargo-about@0.9.3 --features cli --root ~/.local/share/herdr-app-tools`, found through `CARGO_ABOUT` in `mise.local.toml`.
- App home stays `~/.config/herdr-app`, shared with the release build.

## Workflow

1. Start a change: `git switch -c feat/<slug> upstream/master`.
2. Make it, gated behind a setting wherever practical, and commit.
3. Merge and check it on `master`: `git switch master && git merge --no-ff feat/<slug> && mise exec -- just check`. Upstream's code is not `cargo fmt` clean, so match the surrounding style rather than running `cargo fmt`.
4. Try it: `mise exec -- just install`, then restart Herdr.
5. Push the branch: `git push -u origin feat/<slug>`. Bigger changes get an upstream issue first (upstream `CONTRIBUTING.md`).
6. Open the pull request: `gh pr create -R herdrdev/herdr-app --head abhijit-s:feat/<slug>`.
7. Keep it current when upstream moves by merging, never rebasing: `git switch feat/<slug> && git merge upstream/master && git push origin feat/<slug>`. A merge keeps review comments anchored and needs no force-push.
8. Sync and reinstall: `scripts/fork-sync`. It lists branches whose commits are not yet upstream. Once a change lands upstream, delete its branch and its entry below.

### Interface font weight

`feat/ui-font-weight` (fork only): `ui_font_weight` in settings.json (100 to 900, default 400, GPUI's normal weight that the panels draw at unless something sets one) sets the weight of every glyph outside the terminal grid: panels, tabs, overlays, toasts, every mod and the Settings window. It is an offset, not a default: every run the window shapes moves by `ui_font_weight - 400`, within 100 to 900, so text that asks for its own weight keeps its distance from regular text and bold never draws lighter than regular (at 900 they meet). A default-only weight would leave a `SEMIBOLD` label at 600 under regular text at 700. The offset sits where runs are shaped, not in the text style, so it also reaches weights that skip the style cascade (gpui-kit's markdown and highlight bold, plot labels). `HERDR:` changes in `vendor/gpui-pre/src/text_system.rs` (`WindowTextSystem::weight_shift`, `replace_weight_shift`, `resolve_run_font`, used by every shaping path) and `vendor/gpui-pre/src/window.rs` (`Window::set_font_weight_shift`, `with_font_weight_shift`). `AppWindow::render` sets it from `Settings::ui_weight_shift`, beside `set_glyph_thicken`; the terminal grid paints inside `with_font_weight_shift(0)`, so terminals keep `font_weight`. The line layout cache keys on the shifted face, so a change applies live. A variable `ui_font` draws every step through `fix/variable-font-weight`; a family of static faces draws the nearest one it has. The bundled Geist is a single static Regular face, so with nothing else installed it draws every weight (bold included) as Regular; a variable Geist installed on the system, or a variable `ui_font`, draws them all.

- Measured (`tests/weight_ink.rs`, variable Geist Mono for the panels and JetBrains Mono 500 for the grid, 12px at 1x, dark on light): regular / semibold / terminal ink 0.0416 / 0.0613 / 0.0630 at shift -200 (`ui_font_weight` 200), 0.0613 / 0.0767 / 0.0630 at 0, 0.0840 / 0.0974 / 0.0630 at +300 (700). Semibold stays heavier at every shift, and semibold at -200 inks as regular at 0 (both shape at 400).
- Settings window: an "Interface font weight" stepper (steps of 25) under "Interface font" in the Text page's "Size" group. 400 leaves the key out of settings.json. Layouts don't set it.
- Files: `src/settings.rs` (`Person`, `Settings::compose`, `ui_weight_shift`, `problems`, test), `src/window.rs` (`AppWindow::render`), `src/terminal.rs` (the grid's paint), `vendor/gpui-pre/src/{text_system.rs,window.rs}`, `tests/weight_ink.rs`, `Cargo.toml`, `defaults/AGENTS.md`, `defaults/frame/settings/main.js`, `scripts/settings.test.ts`

### Font thickening

`feat/font-thicken`: `font_thicken` and `font_thicken_strength` (0 to 255, default 255), person settings that rasterise terminal glyphs as Ghostty's `font-thicken` does: CoreGraphics font smoothing on, a gray fill of strength / 255 in linear gray, whatever the text color, then tinted. GPUI otherwise picks the smoothing level from the text color's luminance, so dark text on light draws at the lightest level and light text on dark at the heaviest. `ui_font_thicken` and `ui_font_thicken_strength` (same range and default) do the same for every other glyph in the window: panels, tabs, overlays, toasts, every mod and the Settings window. `HERDR:` changes in `vendor/gpui-pre` (`RenderGlyphParams::thicken`, in the glyph atlas key; `Window::with_glyph_thicken`) and `vendor/gpui-pre-macos/src/text_system.rs` (the rasteriser, and 1 more pixel of raster room, as Ghostty pads thickened glyphs). `Window::set_glyph_thicken` sets the strength each frame's paint starts at, deferred draws and tooltips included; `AppWindow::render` sets it from `ui_font_thicken`, beside `set_rem_size`. The terminal paints its grid inside `with_glyph_thicken` at its own strength (None when `font_thicken` is off), which replaces the window's and restores it after, and the row cache's `painted_with` key carries the terminal strength. The atlas key holds the strength, so interface and terminal glyphs at different strengths never share a tile.

- Measured (`tests/thicken_ink.rs`, JetBrains Mono 12px at 1x): font smoothing steps at strengths about 112, 192, 224 and 255, so Ghostty's 30 is its lightest level. Weight 400 with strength 30 inks both polarities alike (0.126), as Ghostty does; weight 250 without thickening inks light on dark 0.134 and dark on light 0.107.
- Measured, interface (same test, dark on light): `ui_font_thicken` at 255 takes panel text from 0.126 to 0.152 ink, while a terminal grid inside it with `font_thicken` off stays at 0.126.
- Settings window, Text page: under Size, a "Thicken interface text" toggle; under Terminal text, a "Thicken" toggle below Weight. Each shows a "Thicken strength" stepper (steps of 16, so it lands on each smoothing level above) while it's on. Off and 255 leave their keys out of settings.json. Layouts set neither, so the rows never say a layout sets its own.
- Files: `src/settings.rs`, `src/terminal.rs` (`glyph_thicken`, `paint_grid`), `src/window.rs` (`AppWindow::render`), `vendor/gpui-pre/src/{text_system.rs,window.rs}`, `vendor/gpui-pre-macos/src/text_system.rs`, `vendor/gpui-pre-{wgpu,windows}` (the new field), `tests/thicken_ink.rs`, `defaults/AGENTS.md`, `defaults/frame/settings/main.js`, `scripts/settings.test.ts`
- Upstream: fork only for now

### Text contrast

`feat/text-contrast`: `text_contrast` and `ui_text_contrast` (0 to 1, default 0), person settings that sharpen glyph edges when they're blended, without widening the strokes. The monochrome-sprite fragment shader moves the glyph's coverage toward smoothstep by the setting: `alpha' = mix(alpha, alpha² (3 − 2 alpha), contrast)`. The curve is symmetric about 0.5, so faint edge pixels fade, nearly solid ones fill, and a stroke keeps its ink. GPUI's wgpu and DirectX backends already apply Zed's DirectWrite-style `enhance_contrast`, `alpha (k + 1) / (alpha k + 1)`, with a global, luminance-scaled `k` and a gamma correction. The Metal backend has no curve. Zed's curve is not reused here: it raises every partial pixel, so it adds ink as thickening does. Measured on Metal at k = 1, it added 14% ink to light on dark and 17% to dark on light. Its luminance factor is 0 for light text, so it would leave light-on-dark terminal text unchanged. The wgpu and DirectX backends apply the S-curve after their own correction, so 0 leaves every backend as it was.

`HERDR:` changes are in `vendor/gpui-pre/src/scene.rs` and its cbindgen copy `vendor/gpui-pre-apple/vendor/gpui/src/scene.rs`. They add `MonochromeSprite::contrast` and an 8-byte-aligning `contrast_pad`, making the sprite 30 words. They are also in `vendor/gpui-pre/src/window.rs` (`with_glyph_contrast`, `set_glyph_contrast`, and `paint_glyph` stamping the sprite), and in the `sharpen_coverage` function in `vendor/gpui-pre-apple/src/shaders.metal`, `vendor/gpui-pre-wgpu/src/shaders.wgsl` and `vendor/gpui-pre-windows/src/shaders.hlsl`. The WebGL decoder reads 30 words. On DirectX, subpixel sprites read their own `SubpixelSprite` buffer, which has no `contrast`, instead of `MonochromeSprite`'s. Contrast is applied at blend time, so it isn't in the glyph atlas key: interface and terminal glyphs share tiles. SVG icons draw at 0. `AppWindow::render` sets the window's contrast from `ui_text_contrast`, beside `set_glyph_thicken`. The terminal paints its grid inside `with_glyph_contrast(text_contrast)`. The row cache keeps shaped lines, not sprites, and re-reads the contrast each paint, so `painted_with` doesn't carry it.

- Measured (`tests/text_contrast.rs`, JetBrains Mono at 12 device px, headless Metal). Edge share is the share of inked pixels with coverage between 0.2 and 0.8, and ink is the mean coverage over the text's box:

| Text | Contrast 0 | 0.5 | 1 | Ink at 0 → 1 |
| --- | --- | --- | --- | --- |
| Light on dark | 0.440 | 0.390 | 0.360 | 0.0711 → 0.0719 (+1.1%) |
| Dark on light | 0.503 | 0.433 | 0.374 | 0.0588 → 0.0590 (+0.3%) |

- For comparison, `font_thicken` 255 takes dark-on-light ink to 0.0711 (+21%). `ui_text_contrast` 1 takes the panels' edge share from 0.440 to 0.360, while a terminal grid inside it at 0 stays at 0.440.
- Settings window, Text page: under Size, an "Interface contrast" stepper; under Terminal text, a "Contrast" stepper below Thicken. Both step by 0.1 within 0 to 1. At 0, the key is left out of settings.json. Layouts set neither.
- Files: `src/settings.rs`, `src/terminal.rs` (the grid's paint), `src/window.rs` (`AppWindow::render`), `vendor/gpui-pre/src/{scene.rs,window.rs}`, `vendor/gpui-pre-apple/{src/shaders.metal,vendor/gpui/src/scene.rs}`, `vendor/gpui-pre-wgpu/src/{shaders.wgsl,shaders_webgl.wgsl,wgpu_renderer.rs}`, `vendor/gpui-pre-windows/src/shaders.hlsl`, `tests/text_contrast.rs`, `defaults/AGENTS.md`, `defaults/frame/settings/main.js`, `scripts/settings.test.ts`
- Upstream: fork only for now

### Popup command

`feat/popup-command` (branched from `master`, fork only): `terminal.popup {argv, cwd?, hold?, wait?, width?, height?}` starts a program on this computer as `hc run --bg --no-parent` does (`rm` unless `wait`) and opens the `terminal.peek` overlay for it in the same step, so there is no retry while the window learns about the terminal. `herdr-app popup [--cwd DIR] [--hold] [--wait] [--size WxH] [--] cmd args…` drives it over the control socket; with `--wait` it sends `{"wait": terminal}`, which the window answers from the core's events once the terminal finishes, then removes the terminal, and the CLI exits with its exit code, 128 + the signal for a program a signal killed (the core's `signal`), or 1 (removed before it ended, the window is not open or the popup failed). The popup's ✕ and backdrop only hide it and the program keeps running: `POPUP_CLOSE_ENDS_PROGRAM` in `src/window.rs` flips that, through the peek bar's `close_ends_program` prop. A new popup ends the program the last `terminal.popup` started, whether that popup is open or hidden (`popped` tracks it, with the core's `created_ms`, until it is ended or a listing shows it finished, gone or another terminal at its address, since addresses come back after a core restart; a wait popup's terminal stays until its waiter has the exit code). A `terminal.peek` of an existing terminal is never ended, and a plain `terminal.peek`, such as a link clicked in a popup, ends nothing: it only hides an open popup, which the next popup still ends. It replaces the logic of the `herdr-popup` shell script in dotfiles, which is now a wrapper.

- `--hold` reads one key with `stty` and `dd`, which any `sh` has (dash, Linux's `/bin/sh`, has no `read -n`).
- Timeouts: the control server gives `terminal.popup` 15 s (`POPUP_ANSWER_WITHIN`), past the 10 s `Core::call` may take for `terminal.run` on the UI thread, and the CLI waits 2 s longer. If the CLI gives up anyway, the reply channel is gone when the window answers, and the window ends and removes the wait popup (`abandon_popup`) instead of keeping it.
- While a request waits, the server checks its stream for a hang-up every 500 ms (`await_reply`, `hung_up`): Ctrl-C on `--wait` drops the waiter, and the program keeps running. On Unix a hang-up is `POLLHUP` (asked for with `POLLOUT`, which macOS needs to report it), so a client that only shut its writing half after the line (`printf … | nc -U`) is still waited for and gets its answer. A finished wait popup nobody has asked about keeps its answer and its terminal for `WAIT_KEPT` (60 s), then both go (`expire_waits`); closing or quitting the window removes the finished ones (`rm_finished_waits`).
- `--size`: a side up to 1 is a fraction of the window and one from 50 is px; between them (`1.5`) is a usage error, more likely a mistyped fraction than a tiny popup.
- Files: `src/commands.rs`, `src/window.rs` (`popup`, `Popped`, `replace_popped`, `forget_gone_popped`, `open_peek`, `abandon_popup`, `end_terminal`, `wait_for`, `settle_waits`, `expire_waits`, `rm_finished_waits`, `popup_hold_argv`, test `popup_peeks`), `src/control.rs` (`popup`, `parse_popup`, `exit_status`, `serve`, `await_reply`, `hung_up`, tests), `src/hc.rs` (`Core::start`, `Core::start_record`, `EventLines::ended`, test core `answering`), `src/main.rs`, `defaults/mods/peek/main.js`, `defaults/AGENTS.md`, `docs/commands.md`
- Upstream: none yet

### System notifications

`feat/system-notifications` (branched from `master`, fork only): an agent alert ("<name> needs you", "<name> hit an error", "<name> finished") also goes to the system's notification center through GPUI's `show_system_notification`, titled as the toast with the agent's own message (its 7501 `msg`, when it gave one) above "space / tab" as the body and tagged `herdr-agent:<address>`, so a newer alert for the same agent replaces the older one. `system_notifications` in settings.json says when: `background` (default; only while Herdr's window isn't key), `always`, or `off`; never while the person is looking at that agent (`alert::should_notify`). Clicking one activates Herdr and runs `agent.focus` for it, as the toast does; it is dismissed once the agent is looked at, starts working again or goes away. `dock_bounce: true` calls `request_attention` for "needs you" while Herdr is in the background. `alert_command` (a string run by `/bin/sh -c`, or an argv array) runs fire-and-forget in place of the system notification, under the same rule, with `HERDR_AGENT_STATE` (blocked|error|done), `HERDR_AGENT_PREV_STATE`, `HERDR_AGENT_APP`, `HERDR_AGENT_NAME`, `HERDR_AGENT_ADDRESS`, `HERDR_AGENT_PLACE`, `HERDR_ALERT_TITLE`, and the agent's own 7501 words as given (`HERDR_AGENT_MESSAGE` from `msg`, `HERDR_AGENT_KIND` from `kind`, `HERDR_AGENT_TITLE` from `title`; empty when absent, read from the terminal's record in the core's listing by `alert::Said::of`), so the herdr TUI's and tuios's `notify` adapters have a Herdr counterpart. The vendored GPUI posts nothing unless the app runs from a bundle (its `NSInternalInconsistencyException` guard), so dev builds stay silent. Settings window: a "System notifications" choice and a "Bounce the Dock icon" toggle under Alerts.

- An `alert_command` starts in the home folder (the app's own is `/` when opened from the Finder) and in its own process group; still running after 30 s, the whole group is killed (`alert::reap`), so a hung one doesn't keep its thread and programs forever. One that doesn't start posts the system notification instead (`alert::Sent::Fallback`), and an error toast says why, once per distinct reason (`alert_command_errors`, cleared when a settings reload changes `alert_command`). ### Hidden terminals free their drawing caches

`perf/hidden-caches` (branched from `master`, fork only): a terminal off screen for a few seconds frees what drawing kept for it. ### Spinners turn without a draw

`perf/spinner-repaint-only` (branched from `master`, fork only): a mod's `svg(...).spin(ms)` turns with no render, layout or paint of anything, its view's or the window's. GPUI marks every ancestor of a notified view dirty and renders the root view on every draw, so the 100 ms wake gpui-kit's `spin_layer` gave its ShellRoot ran `AppWindow::render` and the whole window's prepaint and paint per step (the bench's `idle-busy-bg`: ~8 window draws a second with no terminal drawn). GPUI now has spinning sprites: `Svg::spinning(period)` / `Window::paint_spinning_svg` paint a monochrome sprite whose `pad` slot (which no shader reads) holds its period, so a cached view replaying the sprite replays the spin. `Window::present` turns every spinning sprite of the frame on screen to `gpui::spin_clock_ms()`, and while that frame has one, a timer asks for a present-only frame every `SPIN_STEP` (100 ms, ~10 fps) through the platform's frame source. gpui-kit's `spin` draws such an svg in place, so the hosted spinner layer (`Spin`, `spin_layer`, `build_view`, `Fade` and the inline fallbacks) is gone, and a spinner keeps its true stacking, opacity and clipping. A spinner turns about its drawn sprite's center (within a device pixel of its element's center).

- A step already scheduled when a draw took the spinners away presents nothing; steps wait while the window is hidden (`Window::visibility`) and start again when it is visible.
- `Scene` keeps `has_spinners`, set when a spinning sprite is inserted (cached replay inserts too) and cleared with the scene, so a present without spinners skips the scan.
- `Svg::spinning` works for an `external_path` or inline data svg as well as a `path` one.
- A spinner drawn fully transparent (opacity or colour alpha 0) is left out of the frame, so it doesn't keep the window presenting. `spin(ms)` ignores a non-finite `ms` and clamps the rest to 100 ms – 1 hour; the gpui-kit tests sit outside the workspace, so a root-crate test (`spin_with_an_absurd_period_draws_without_panicking`) hands Infinity, NaN and 1e300 to `spin` through the script bridge (`__apply`; `.spin()` itself rejects them in JavaScript) and renders.
- The turn is not reflected in the sprite's bounds for layer ordering and clipping, so a spinner should be round or symmetric within its box.

### Pane arrangements

`feat/pane-arrange` and `feat/auto-arrange` (branched from `master`, fork only for now): `pane.arrange {mode, tab?}` rebuilds a tab's existing panes (default: the shown tab) into a preset shape with even sizes, as tmux's `select-layout` and tuios's tiling modes do. Modes: `tiled` (grid, `ceil(sqrt(n))` across, row by row, a short last row's panes widen: tmux's tiled), `bsp` (dwindle: each pane takes half of what's left, splitting right, down, right…), `master` (the focused pane on the left half, the rest stacked on the right), `columns`, `rows`, `next` (the mode after the tab's last one, from `tiled`) and `off` (below). Panes keep their block whole (id, terminal or mod, name), so nothing restarts; only the row/column containers are new, and the tree is saved and synced like a manual split. Order is reading order (by top edge, then left edge, from the current sizes), which every mode's output preserves, so cycling never shuffles panes except that `master` moves the focused pane first. Focus stays; a zoomed pane unzooms. The tab's mode is this screen's choice (`TabView.arrange` in the saved view, not the shared document) and shows to mods as the tab's `arrange`. Keys: `cmd-shift-space` (macOS) and `ctrl-shift-space` (Linux, Windows) run `pane.arrange:next`; existing untouched key files get it through upstream's shipped-originals upgrade (f524898), edited ones need the line added. The palette lists "Next pane arrangement" and each mode.

- Auto-arrange: a tab keeps its mode (yabai's per-space layout), so every pane split into it or closed in it, by any path (`pane.split`, `pane.close`, a mod pane, a terminal kept or adopted for an agent, a program that ends), runs the mode again with even sizes. The hook is in `Model::split_tree` (used by `split_with` and by the window's initial-size guess) and `Model::remove_pane`, which own the tab's view state; a document arriving from another screen replaces the tree without them, so screens with different modes never re-arrange each other's changes. Order is the tab's reading order before the change, the new pane inserted right after the pane it split (so in `bsp` it takes half of that pane's space) and a closed pane dropped (`arrange::arrange_in`). Re-arranging never picks a master, so `master` keeps the pane in its master slot; only `pane.arrange master` makes the focused pane master. Focus and zoom are the plain split's and close's (a split focuses the new pane and unzooms). A dragged divider holds until the next split or close; `pane.swap` and pane drags keep the mode, and the next arrangement goes on in the new order. A tab holding blocks other than panes splits and closes plainly. `pane.arrange off` (palette "Arrange panes: off") clears the mode and leaves the panes where they are; `next` never picks it. `default_arrange` in settings.json (a mode name; absent or anything else: none) gives tabs made on this screen (`Model::add_tab`, `add_space`) that mode; the Settings window's Look page sets it under Panes ("New tabs arrange").

### Focus follows mouse

`feat/focus-follows-mouse` (branched from `master`, fork only): `focus_follows_mouse` in settings.json (default off) focuses a terminal pane, a tab's or a layout's terminal block, once the pointer rests on it for `focus_follows_mouse_delay_ms` (0 to 2000, default 150; clamped when read), through `pane.focus` as a click would. The delay is a debounce: it runs from after the pointer rests, every real move starts it over, so sweeping across a pane on the way somewhere else doesn't focus it; at 0 ms the first move onto a new pane focuses it at once. Only a real pointer move counts: content scrolling or panes moving under a still pointer, and moves under 1 px (jitter, which neither starts nor delays a wait), keep the focus. After any key down, or a focus change made some other way (menu-bound keys, clicks, mods), a wait may only start once the pointer has gone more than 4 logical px from where it was then, so a pane the keyboard focused keeps the focus while the hand rests on the mouse. It never moves while a button is held (selections, pane and divider drags, link clicks), while a dialog, popup, peek or menu is open (toasts and window overlays don't count), while Herdr isn't the active window, or onto the pane already focused; a press, the pointer leaving the pane or the window, or any of those arriving cancel the wait. `focus.toggle_follows_mouse` flips the setting in settings.json and says so in a toast. Keys pressed while it is off hold the pointer too, so a key that turns it on keeps the focus where it is until the pointer moves 4 px. `write_person` returns `PersonSaved` (saved, broken or write failed); when it isn't saved the toast is a warning, "Focus follows mouse: on (not saved: settings.json has errors)" or "… (not saved: cannot write settings.json)", and a control-socket caller gets that as an error (the zoom keys apply unsaved). The rules are a pure `Follow` state machine (`still`, `moved`, `keys`, `fire`, `cancel`) the window feeds from its root's mouse-move, mouse-exit, mouse-down and key-down listeners; the pane under the pointer is the shown terminal block (the active tab's, zoom applied, or the layout's) whose painted bounds hold the pointer, unless a floating block or a window overlay is over it there, checked again against the pointer's position when the wait ends (hidden blocks keep stale bounds and terminal hover, so neither is trusted alone).

### Subpixel smoothing

`trial/subpixel` (merged into `master`, fork only): subpixel (LCD) text smoothing on macOS, off by default. `text_rendering` (terminals) and `ui_text_rendering` (panels) take `"grayscale"` (default) or `"subpixel"`; `subpixel_order` takes `"rgb"` (default) or `"bgr"`. Subpixel only draws on an opaque window on a 1x, unrotated display; on the 2x displays and anywhere else text stays grayscale, and a window moved between displays switches on its next frame. It started as a trial of the experiment listed under "Rejected text experiments" below, judged on the 1x LG display: the interface uses it there; terminal text stays grayscale, which matches Ghostty.

CoreGraphics makes no per-channel coverage on macOS 27, so subpixel glyphs are rasterised by swash. CoreText still shapes, picks glyphs and lays out advances (they match swash's to 0.00000 px). swash draws the outline at 3× horizontal resolution (`Render::transform(scale(3, 1))`) and FreeType's default 5-tap filter, [8, 77, 86, 77, 8]/256, turns each pixel's three subpixels into red, green and blue coverage (`vendor/gpui-pre-macos/src/lcd.rs`). Faces are opened once per font from the bytes Herdr embedded, a mapped single-face file, or the tables CoreText hands out (collections), at the variation CoreText draws. swash has no smoothing dilation and its plain coverage is about 17% lighter than CoreGraphics' (JetBrains Mono 12), and CoreGraphics grows glyphs more along the rows than across them. So outlines are emboldened separately across and along the rows (`Outline::embolden(x, y)`), by one growth per font (face, size in device pixels, and thicken or the color's dilation): the growth that inks a calibration set exactly like CoreGraphics' grayscale while matching each glyph's rows' ink first and its pixels second (`lcd::fit`: least squares, linear in the growth, under the ink constraint). The set is printable ASCII with lowercase counted twice (evenly, Geist 13 inked 2% over grayscale on interface text; lowercase alone, 1–3% under). It is fitted once, when the font's first subpixel glyph enters the atlas (0.7–3.9 ms in a debug build, each glyph drawn by swash plain and grown 0.1 px each way at one sample per pixel in CoreGraphics' box), and cached. With `font_thicken` on, CoreGraphics draws the set at smoothing levels 0 and 4 and the growth for any level is interpolated between the two fits (`lcd::Weight`); the level is a continuous function of the strength (`lcd::thicken_level`): 0 at strength 0, through the middle of each of CoreGraphics' levels 1 to 3, to 4 at 255. CoreGraphics' own levels step at strengths 100, 165, 208 and 241, so grayscale adds no weight below 100 and jumps about 5.5% at each step, where subpixel adds some at every strength and lands within three quarters of a step of grayscale everywhere. With it off, the fit is against grayscale at the color's dilation. Fitted values: JetBrains Mono 12 at strength 30, 0.073 px across by 0.117 along (0.063 by 0.115 at level 0, 0.230 by 0.150 at 4); Geist 13 at strength 192, 0.198 by 0.093. A growth fitted to each glyph (the build before this one) matched each glyph's ink and rows but gave neighbouring glyphs different stems: `i` 22% wider than `l`. swash reads one winding for a whole outline and gets some glyphs' wrong (JetBrains Mono's `i`, whose two contours its whole-outline area test reads as one backwards polygon), so a positive growth shrinks them: each glyph's sign comes from whether swash's probe growth adds ink (`lcd::Samples::outward`, cached per glyph), and it grows by the font's growth times that sign. swash grows an outline right and up, its left and bottom edges fixed; grown by a negative strength it grows left and down, so those glyphs are moved back by twice the strength to sit as the rest do. A face swash can't open falls back to its grayscale coverage. Emoji stay as they are.

Metal gains what Zed's Linux and Windows backends have: a BGRA `Subpixel` atlas kind, a `subpixel_sprite` shader pair whose second output blends each background channel toward the text color by its own coverage (dual-source blending, `MTLBlendFactor::Source1Color`), and the `SubpixelSprites` batch. Blending happens in the same gamma space as monochrome sprites, with no Zed gamma correction, so three equal coverages draw exactly as grayscale. `text_contrast` applies per channel. `SubpixelSprite`'s alignment `pad` became `contrast` (same layout; the wgpu and DirectX shaders still read it as pad). `Window::with_glyph_subpixel` / `set_glyph_subpixel` ask for subpixel glyphs under the app's platform-default mode, as the thicken and contrast pairs do; `should_use_subpixel_rendering` still requires an opaque window and `is_subpixel_rendering_supported()`, which macOS answers from the window's screen (backing scale 1, `CGDisplayRotation` 0), cached and re-checked when the screen or scale changes. `gpui::set_subpixel_bgr` swaps channels in the shader.

### Handlers inside list rows

`feat/vlist-row-handlers` (branched from `master`, fork only): a row a lazy list's item renderer returns (`v_virtual_list`, `h_virtual_list`, `uniform_list`, `list`) may register its own handlers: `on_click`, `on_hover`, `on_mouse_down`/`on_mouse_up` (any button), `on_mouse_move`, `on_action`, `on_open_change` and the rest of gpui-kit's handler methods, on the row and on anything inside it, including a `HoverCard`'s trigger and content. `cx.stop_propagation()` in a row's handler keeps the press from the list's `on_item_click`, which still works as before. Upstream refuses all of these with an error naming `on_item_click`, because a handler belongs to the snapshot that registered it and a row is rebuilt every frame, so per-row handlers would pile up for as long as the view stood.

Each batch the item renderer describes records its handlers into a callback generation of its own (`render_virtual_items`) and commits it with a `CallbackLease` that retires the generation on drop. Every row of the batch holds the lease from a no-op mouse-move listener (`holding`), which GPUI keeps from a painted element until the next frame's listeners replace it, so a batch lives exactly as long as its rows are on screen. The measuring pass's batch is never painted and is released when layout drops it, and a batch that registered nothing takes no lease and no wrapper. A handler belongs to the row it was drawn into, so a press after a scroll reaches the row now under the pointer. Layout-phase renderers other than a list's item renderer (a dock's chrome, a registered component's element callback) still refuse handlers, with a message that no longer points at `on_item_click`.

- Row state a handler changes (hovered, pressed, dragging) lives on the view, keyed by the list's `get_key`: a row remembers nothing between frames. A `HoverCard` in a row keeps its open state in GPUI's window state under its id, so its id must be unique per row (`card-${key}`).

### Dim when inactive

`feat/unfocused-dim` (branched from `master`, fork only): `unfocused_dim` in settings.json (0 to 1, default 0, off), as Rex does. While the Herdr window isn't the active one, each terminal's text, sprites, fallback icons and link underlines blend that fraction toward the terminal's background. Backgrounds, selection and find highlights (painted from the frame, outside the text's colours), the cursor and the panels keep their colours. The switch is instant both ways, with no fade.

- `paint_grid` reads GPUI's `window.is_window_active()` rather than the window's polled `window_active`: GPUI refreshes the whole window when activation changes, so the paint already reruns at the moment of the change, where the poll would lag by up to 400 ms.
- The dim is applied while a row's drawing is built (`row_ops`, through `Fade`), since shaped lines carry their colours. The effective dim and the background it fades toward are part of `painted_with`, so a change of either rebuilds every row once and a steady state reuses the kept rows as before.
- Settings window: a "Dim when inactive" stepper (steps of 0.1) on the Text page under Terminal text, through the same `contrast` helper as `text_contrast`. Layouts don't set it.
- Files: `src/settings.rs` (test `unfocused_dim_defaults_off_and_validates`), `src/terminal.rs` (`dimmed`, `Fade`, `paint_grid`, test `dimming_blends_text_toward_the_background`), `src/window.rs` (test `terminal_text_dims_while_the_window_is_inactive`), `defaults/AGENTS.md`, `defaults/frame/settings/main.js`

### Rejected text experiments

Two text-quality experiments measured against the shipped thicken, contrast and weight settings, and not kept. The numbers are here so neither is tried again without a new reason.

- **Gamma-correct (linear-light) glyph blending.** A Skia-style preblend (`SkMaskGamma`): a per-sprite gamma in `MonochromeSprite`, the shader assuming the text's perceptual inverse as background. Headless Metal readback, JetBrains Mono 12 px: at gamma 2.2 plain light-on-dark ink went from 1.21× dark-on-light to 1.91×; with thicken 30 and contrast 0.2 (equal ink in both polarities, 1.00) it split to 1.61× and moved light-on-dark ink +23% away from the Ghostty match. Equal polarities needed gamma ≈ 0.6, the opposite of linear light. The polarity gap in Herdr comes from CoreGraphics dilating light text more (`glyph_dilation_for_color`), not from gamma-space blending, and thicken already removes it by giving both polarities one mask. Prototype commit `f7a2a85` (branch deleted).
- **Subpixel (LCD) smoothing on macOS.** CoreGraphics produces no per-channel coverage on macOS 27 with any public or private smoothing setting tried (`setShouldSmoothFonts`, `AppleFontSmoothing`, `CGContextSetFontSmoothingStyle`), so it would need swash rasterising 3× horizontally plus FreeType's 5-tap filter, with CoreText keeping shaping and advances (they match to 0.00000 px). About half the plumbing exists from Zed's Windows/Linux work (`TextRenderingMode`, `SubpixelSprite`); Metal lacks the subpixel atlas kind, shader and batch. Estimated 5–8 days and ~1,000 fork-only lines. Not built at first (since built, see "Subpixel smoothing" above): swash can't reproduce CoreGraphics' smoothing dilation, so it drops the Ghostty match thicken was tuned for, it puts colour fringes into screenshots and screen shares, and side-by-side 1x renders showed fringing without a clear sharpness gain.
