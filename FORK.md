# Fork changes

This fork of [herdrdev/herdr-app](https://github.com/herdrdev/herdr-app) is the Herdr build used day to day. It carries small, focused changes that each go upstream as their own pull request, and it tracks upstream by merging `upstream/master` into `master`.

This file is the inventory of what diverges. Update it in the same commit that adds, removes or upstreams a change.

Where a change belongs (app Rust core, mods or herdr-core) and the order changes go upstream are decided in [FORK-ADR-001](fork/adr/ADR-001-fork-architecture-stance.md), an architecture decision record (ADR). Each change's section records its answers to upstream's three questions and its upstream verdict. The per-feature audit behind it is [fork/upstream-audit-2026-11-08.md](fork/upstream-audit-2026-11-08.md).

## Branches

- `master`: `upstream/master` plus every change below, merged in. This is what gets built and installed.
- `feat/<slug>`, `fix/<slug>`: one change each, branched from `upstream/master` so its pull request carries nothing else.
- `FORK.md`, `scripts/fork-sync` and `mise.local.toml` (untracked) exist only on `master`.

## Setup

- Toolchains match upstream CI (continuous integration): Rust 1.95.0 and Zig 0.16.0, pinned per folder in `mise.local.toml` (listed in `.git/info/exclude`). Run commands through `mise exec --`.
- `just install` builds a release into `~/Applications/Herdr.app` and points `~/.local/bin/herdr-app` at it. Quit and reopen Herdr to use it. herdr-core is installed separately and is not rebuilt.
- `just notices` needs cargo-about 0.9.3: `cargo install --locked cargo-about@0.9.3 --features cli --root ~/.local/share/herdr-app-tools`, found through `CARGO_ABOUT` in `mise.local.toml`.
- App home stays `~/.config/herdr-app`, shared with the release build.

## Workflow

1. Start a change: `git switch -c feat/<slug> upstream/master`.
2. Make it, gated behind a setting wherever practical, and commit.
3. Merge and check it on `master`: `git switch master && git merge --no-ff feat/<slug> && mise exec -- just check`. Upstream's code is not `cargo fmt` clean, so match the surrounding style rather than running `cargo fmt`. The same goes for `defaults/AGENTS.md`: upstream hard-wraps most of it at about 75 columns, so fork text there is wrapped the same way, which keeps merges clean, and stays a map of rules with short examples, the detail going here and in `defaults/herdr.d.ts`.
4. Try it: `mise exec -- just install`, then restart Herdr.
5. Push the branch: `git push -u origin feat/<slug>`. Bigger changes get an upstream issue first (upstream `CONTRIBUTING.md`).
6. Open the pull request: `gh pr create -R herdrdev/herdr-app --head abhijit-s:feat/<slug>`.
7. Keep it current when upstream moves by merging, never rebasing: `git switch feat/<slug> && git merge upstream/master && git push origin feat/<slug>`. A merge keeps review comments anchored and needs no force-push.
8. Sync and reinstall: `scripts/fork-sync`. It lists branches whose commits are not yet upstream. Once a change lands upstream, delete its branch and its entry below.

## Changes

### Build identifier

`feat/build-tag` (branched from `master`, fork only): a fork build says which commit it is, beside an unchanged version. `build.rs` runs git (`fork_build.rs`) and sets `HERDR_FORK_BUILD` to `fork.<short sha>`, with `.dirty` when tracked files differ from HEAD; without git (a tarball) it is unset. No `Cargo.toml` edit, so upstream syncs stay clean.

- Shown: `herdr-app --version` prints `herdr-app 0.1.13 (fork 0990622)`; Settings shows `Herdr 0.1.13 (fork 0990622)` and `herdr-core 0.1.18 (fork 8cc5ec1)`, and This computer `hc 0.1.18 (fork 8cc5ec1)` under Machines. The core's build is read from the `build` field of its `server.status` (the herdr-core fork adds it), kept in `update::CoreInfo.build`.
- The version stays upstream's everywhere it is compared or sent: the core compatibility check (`hc::check` on `hello`), app and core update checks (`update::newer`, `core_bin::update_to`, `after_update`), telemetry, feedback, layout `cloned_from` and update notes all read `CARGO_PKG_VERSION` or the core's `version` alone. `herdr-app status` and `ls` report no version. Readers of a `--version` line cut a fork build's ` (fork …)`: `core_bin::version` (finding and checking a core) and `update::version_of` (a staged app update).
- Rebuilds: build.rs reruns when HEAD, its reflog, its branch or `packed-refs` change (paths from `git rev-parse`, so worktrees work), and on edits under `src` and `defaults`. Not on index changes: editors and `git status` rewrite the index, and each rerun recompiles the app. So an edit elsewhere, or a staged-only change, does not mark the build `.dirty` until something else reruns it. Worktrees need their own target dir (the default): Cargo hashes a package by its path within the workspace, so a shared `CARGO_TARGET_DIR` could keep another worktree's build. After an in-app core update the core's build is cleared until its status arrives on reconnect.
- Tests: `fork_build::tests` (the `--version` line, a well-formed build, git in a temporary repository: no git gives none, a commit gives its sha, an edit adds `.dirty`, untracked files do not; the core's version and build reach Settings apart), `core_bin::tests::only_a_binary_that_says_hc_counts` (a fork core's line still reads as `hc 0.1.1`), `scripts/settings.test.ts` (`forkTag`).
- Files: `build.rs`, `fork_build.rs`, `src/fork_build.rs`, `src/main.rs`, `src/update.rs`, `src/core_bin.rs`, `src/window.rs`, `defaults/frame/settings/main.js`, `scripts/settings.test.ts`, `tests/fixtures/core-bin/herdr-core-fork`

### Pane and agent labels

`feat/agent-label` (branched from `master`, fork only): what a pane or agent is called is one app-level value, `label`, with `session` beside it, on `panes()`, `agents()` and `herdr-app ls`, so mods stop carrying their own copies of the "telling title" rule. `src/pane_label.rs` holds the resolver and the rule.

- `label`, first that applies: the pane's `pane.rename` name (one with a letter or digit), its `auto_name`, its title when telling, `session`, the program's name, the terminal's address. A mod pane: its name, else the mod. `title` stays the raw title.
- Telling: judged on the title less what leads up to its first letter, digit or path (`shown_title` already cut spinners), shown trimmed but otherwise as set, so `✓ build passed` and `[3/5] Building` keep their lead: not empty or only digits, not the program's name (any case), not its command line (first word the program's key or name, by basename), not a path (`~`, `/`, `C:\`, `C:/`, `\\server`), no `@`, and not `THROWAWAY`: one documented regex constant for anything holding a UUID (universally unique identifier), `claude-prompt-…`/`tmp.…` files and an editor's ` - Nvim`/` - VIM` title (Neovim as Claude Code's Ctrl+G editor leaves `claude-prompt-<uuid>.md + (/private/tmp/…) - Nvim`). Not a setting: the patterns describe tools' own titles, and a setting would add a Settings row, validation and docs for something nobody has asked to tune.
- `auto_name` second, not after `session`: it is only set at a bare shell whose title is generic, which is never an agent, and the shipped `pane` and `terminals-pane` headers already put it before the title (a folder-name title such as `src` would otherwise beat it).
- `session`: the session's own name from the program's session file, a programs-table field `session_name` (`{file, field, when?}`, the `resume.session` shape, checked the same way; Claude Code ships `~/.claude/sessions/{pid}.json` `name`), for the terminal's foreground process, and only while that process is the foreground (a cached name is matched on pid, so an agent that quit never lends its name to the shell). `pane_label::Sessions` caches it per terminal by pid and file mtime: a look runs after a terminal listing or every 3 s (`SESSION_RECHECK`), stats the files off the main thread and reads one only when its pid or mtime changed; a name that changed publishes. Terminals on other machines get null. It replaces pane-named's JS (JavaScript) lookup and its `claude.sessionNames` shared key; the `herdr.session.claude` label is not used (it can vanish from a live terminal).
- Perf: labels are resolved in `publish` (titles, names, foregrounds, listings), never per frame; `herdr-app ls` reads the published map.
- Shipped mods: `agents` (`title()` and its rows), `terminals-pane`, `win98` window titles and the `pane` header read `label`; their local `clean`/title checks are gone. The `pane` header keeps the program's name for an unnamed agent or bare shell. `tabs`, `peek` and `picker` show a program's kind (its name beside its icon), not what a pane is called, and stay as they were. With telling titles, every shipped mod's description under the populated render fixture is byte-identical to before (all 26 entries and win98's window role diffed), and glyph-led titles (`✓`, `[3/5]`) are pinned in the render test. Intended differences: a renamed pane's name wins over its title in `agents` rows and `win98` titles, and `agents` keeps a leading `✓` or `[` rather than cutting it.
- Tests: `pane_label::tests::{telling_titles_are_shown_as_the_program_set_them, titles_that_say_nothing_are_not_telling, a_label_takes_the_first_that_applies, a_session_files_name_counts_when_it_names_something, session_names_are_read_once_per_process_and_again_when_the_file_changes}` (fixture session files: missing, bad JSON, renamed, another pid), `programs::tests::session_name_files_are_checked_and_a_persons_replaces_the_shipped_one`, `mods::render_tests::mods_name_panes_by_their_label`, `window::tests::pane_labels_follow_changes_not_frames` (own process: 30 frames resolve no label; a title change and a new foreground each resolve both panes once), `scripts/agents.test.ts`. ### Rex theme importer

`feat/rex-themes` (branched from `master`, fork only): `herdr-app rex-themes [--dry-run] [--from <themes.json>]` writes `themes/rex-<id>.json` in the app home (`HERDR_APP_HOME` honoured) for each theme of the installed Rex app, read from `/Applications/Rex Beta.app/.../SuperDesignTokens.bundle/.../themes.json`. Rex is closed source, so its theme data is never committed: the importer reads the app on every run and writes only into the person's themes folder, and its tests use an invented fixture in Rex's schema.

- Why a subcommand, not a script: it reuses the app's own theme parser and `app_dir()`, writes with `persist::write_atomic`, and its tests run in `just check` against the real theme loader (`settings::theme_file_problems`, test only); a bun script would have to re-implement both.
- Palette: Rex's `source` (sRGB hex, in the standard red-green-blue colour space) gives `foreground`, `cursor`, `selection` (`selectionBackground`) and `ansi`. Rex's `palette` is the same in display-p3 floats. `background` (the terminal's) is `--super-term-bg`, the pane color a step off the window (`--super-bg`, which becomes `canvas`), so panes read as cards on the window as they do in Rex; a theme without an opaque `--super-term-bg` falls back to `source.background`.
- Named colours: one table, `COLORS` in `src/rex_themes.rs`, maps a Rex token to a Herdr colour only where the meaning matches. Values come from Rex's `cssVariables` (sRGB, its design values); its `semantic` tokens are display-p3 and more saturated, so converting them clips in sRGB. `focus` and `ring` (both from `accentBorder`) are written only when opaque and at 3:1 on the background, else Herdr's readable defaults apply. Setting `surface` and `popover` makes Herdr derive what's left unset the classic way (`paints_own_panels`), which is why `raised` and `ring` are mapped too. `canvas` is Rex's `--super-bg`, which equals the terminal background in 39 of the 41 themes (Rex draws its terminals on `--super-pane`, a step lighter); the palette's background stays the terminal's.
- Light and dark: Herdr tells them apart by the background. A theme Rex calls light whose background reads dark (or the reverse) is skipped with a message; none of the 41 shipped Rex themes is.
- Idempotent: an existing file with the same text is left alone (unchanged), a different one rewritten (updated); nothing but `rex-<id>.json` is touched, and `rex-*` files without a matching Rex theme are kept. A theme with a colour that isn't `#rrggbb` or a CSS (Cascading Style Sheets) `rgb` value, or without 16 ANSI (American National Standards Institute) colours, is skipped with the reason and the rest still written (exit 1). A missing Rex is an error (exit 1), not a crash.
- Tests: `rex_themes::tests::{maps_the_palette_and_the_matching_tokens, light_themes_load_as_light_and_a_mismatch_is_skipped, a_second_run_changes_only_what_changed_and_only_rex_files, a_missing_or_unreadable_rex_file_is_an_error, a_bad_color_skips_that_theme_only, a_focus_and_ring_under_3_to_1_or_translucent_are_left_to_herdr, ids_that_make_no_file_or_the_same_file_are_skipped, the_installed_rex_themes_all_load}` (the last imports the installed Rex's themes into a temporary folder when Rex is on the machine, and checks each loads with `ring` and `focus` at 3:1; nothing kept). Each guard mutation-checked.
- Files: `src/rex_themes.rs`, `src/main.rs`, `src/settings.rs` (`is_light` public, `theme_file_problems`), `defaults/AGENTS.md`
- Upstream: none (Rex-specific)

### Focus colour

`feat/focus-colour` (branched from `master`, fork only): a named theme colour `focus` for the active pane's border, and a person setting `focus_border_width` (1 to 3 px) for its width. The shipped Herdr layout's pane frame draws `"focus": {"color": "focus"}` rather than `"accent"`.

- Colour: `resolve` adds `focus` under both `panel_colors`: the accent in use (`ansi[4]`, or a theme's, look's or settings.json's `colors.accent`, alpha dropped, so a translucent accent draws an opaque border) when it reads at 3:1 on the background, else the same fallback as `ring` (`readable_accent`, shared with `ring`). A theme file's, look's or settings.json's `colors.focus` replaces it with the usual precedence. With an accent at 3:1 or better nothing changes; the five public themes in the author's themes folder whose accent sits under 3:1 (ayu-light, everforest-light-med, melange-light, nord-light, zenburn) draw a readable border.
- Width: `focus_border_width` replaces the layout's `focus` width (`Settings::focus_width`, clamped to 1..3, out of range reported). Every framed pane sits in by the wider of its `border` and `focus` widths (`frame_inset`), and `frame_pane` pads the narrower line out (showing the frame's `background` if it sets one; a hover header is inset by the same pad), so moving the focus never resizes a terminal. Layouts with equal widths (all shipped ones) need no padding; a layout with a wider `focus` than `border` doesn't resize terminals on focus, and one with only a `focus` line leaves that gap around unfocused panes too. Hidden tabs refit when the width changes (`Geometry`).
- Shipped layout: `main.json` changes, so an untouched installed copy is replaced through `installed.json`'s fingerprint (`sync_layouts`), and an edited one is kept as `main-edited` as for any shipped layout change; no snapshot is needed. As with any change to a shipped pane frame, saved pane-frame clicks for `main` (header height, border and focus widths: `PaneClick` in `layout_sync.rs`) are dropped once.
- Settings window: Appearance > Panes: "Focus border" (From theme, or one of the shown theme's ANSI 1 to 6 and terminal foreground at their current values, written to `colors.focus`; a hand-written colour shows as its own swatch) and "Focus border width" (Layout, 1, 2 or 3 px).
- Perf: `focus` is resolved with the rest of the theme at `settings::set` and `reshade`, never per frame; drawing reads it with the same map lookup `accent` took. `frame_border` and `frame_inset` read `settings::get()` (an `Rc` clone) and compare two floats per framed pane per frame, with no allocation.
- Tests: `settings::derivation_tests::{focus_is_the_readable_accent_unless_set, classic_panels_are_the_first_derivation_exactly}` (the golden classic panels leave `focus` out), `settings::tests::focus_border_width_stays_out_unset_and_reports_a_width_outside_1_to_3`, `window::pane_size::tests::{focus_border_width_replaces_the_layouts_focus_width_within_1_to_3, moving_the_focus_never_resizes_a_framed_pane}`, `window::tests::moving_the_focus_keeps_framed_terminals_their_size` (own process), `mods::render_tests::focus_border_rows_show_the_pick`, `scripts/settings.test.ts` (focus border width, focus border). Each guard mutation-checked; the hidden-tab refit on a width change has no test.
- Files: `src/settings.rs`, `src/window.rs` (`frame_pane`), `src/window/pane_size.rs`, `defaults/layouts/main.json`, `defaults/frame/settings/main.js`, `defaults/AGENTS.md`, `scripts/settings.test.ts`, `src/mods/render_tests.rs`

### Hung alert command test

`fix/alert-hung-test` (branched from `master`, fork only): `alert::tests::a_hung_alert_command_is_killed_after_its_limit_with_what_it_started` failed intermittently with "killed, not finished" while other jobs on the machine started and stopped processes. Its shell line ran `sleep 30 & echo $!; wait`: a bare `wait` returns 0 however its child ended, so a `sleep` killed from outside made the shell exit cleanly, which read as Herdr not killing it. The child is a subshell looping on one-second sleeps for 30 s, which a stray kill of a `sleep` (pkill, killall) doesn't end and which a missing kill turns into a failure rather than a hang, and the shell waits on it (`wait $!`); the test requires the shell to end by SIGKILL and says in its message what the shell's status was, how long it took and whether its child was already reaped. No cause inside the test binary was found: no code sets SIGCHLD to ignored, and every other kill in it is `Child::kill` on a child not yet waited for. Herdr's own code is unchanged.

- Tests: the test above; reverting the kill entirely, or keeping only the shell's kill without its process group's, fails it.

### Pane text zoom

`feat/pane-zoom` (branched from `master`, fork only): `pane.zoom_text_in`, `pane.zoom_text_out` and `pane.zoom_text_reset {pane?}` zoom one terminal pane's text (default: the terminal with the keyboard), as Ghostty's per-surface font size does, while `app.zoom_*` keeps zooming everything. macOS binds Ctrl+= (and Ctrl++), Ctrl+- and Ctrl+0 in `global`; Cmd+= and friends stay `app.zoom_*`. Linux and Windows leave the commands unbound, because Ctrl+= is already `app.zoom_in` there.

- Steps: `zoom_step` as for the app: `"point"` moves the pane's own size (`font_size × pane zoom`) by whole points from where it is (the nearest point first from between two), `"tenth"` moves the pane zoom by 0.1 (`Settings::next_pane_zoom`, sharing `step_zoom` with `next_zoom`). Back at 1 the pane is at the default again (None). The drawn size is `font_size × pane zoom × zoom` (`pane_font_size`, each factor snapped to a whole point within float error at `"point"`), so the app's zoom multiplies on top and resetting either keeps the other. Letter spacing scales with the pane zoom as it does with `zoom`; padding stays the app's.
- Where it lives: `TerminalView::text_zoom`, for the life of the view (a pane's terminal; a peek or swapped-in view of the same terminal has its own, and a pane that gets another terminal starts at the default). Not persisted, as in Ghostty.
- Per-pane cell: `text_metrics(window, pane zoom)` returns the cell and text px. At the default it is exactly the old path (`cell_size(window)`, `settings::font_size()`), so panes at the default size do no extra work per frame; a zoomed pane measures with `measure_cell_at` at its own size, following `cell_width` and `cell_rounding`. The grid stores the text px beside the cell (`Grid::font`), and everything that drew or mapped by the global size reads the grid instead: `row_ops`, `fallback_fit`, the block cursor's glyph, the input method's composing text and the kept-row cache key (`painted_with`). Selection, mouse and pixel mouse reports, wheel scrolling, links, the scroll thumb, kitty image placement, sprites and Nerd icons already read the grid's cell. `fit_hidden_tabs` fits each hidden terminal at its own size (`TerminalView::fit(area, window)`, from `shown_area`); new terminals still start at the window's cell. A zoom change reflows on the next prepaint through `Grid::fit`, which resizes the screen and tells the program, as a pane resize does.
- Keys and passthrough: with the setting on, Ctrl+- (^_, undo in zsh, readline and emacs) and Ctrl+0 don't reach programs; turn `pane_zoom_keys` off to give them back. ### Cell rounding

`feat/cell-round-nearest` (branched from `master`, fork only): `cell_rounding` in settings.json, `"outward"` (default) or `"nearest"`, for how the grid snaps to whole device pixels: the row height (ascent + descent, × `line_height`) always, the cell width when `cell_width` is `"pixel"`. A separate key rather than a third `cell_width` value, because the row snaps in both `cell_width` modes.

- Rule (`CellRounding::whole`, used by `row_height` and `cell_width`): `"nearest"` puts each dimension at the nearest whole device pixel of the font's own metric, at least one. That is the closest a pixel grid can get to the font's designed advance and line height: never more than half a device pixel off, either way. `"outward"` (width down, row up) is up to a whole pixel off, always in the same direction, so zoomed text drifts from the font's spacing (JetBrains Mono 13 at 1x: 7.8 × 16.9 becomes 7 × 18 outward, 8 × 17 nearest). Ghostty sizes cells the same way (`Metrics.zig`, `@round` of the face's width and height), which confirms it rather than being the reason.
- Default `"outward"`: it keeps every existing grid where it is. `"nearest"` moves the grid by a device pixel at many sizes, so it is opt-in.
- What `"nearest"` moves, by `cells_follow_each_fonts_metrics_by_the_rounding_rule` (JetBrains Mono, Geist Mono, Menlo, Monaco and Courier New, 9 to 24 pt, 1x and 2x, line height 1): 83 of the 120 font/size/scale cells change by one device pixel in width, height or both (counted once from the test's metrics; no test asserts the count). JetBrains Mono at 12 (1x and 2x) and 15 (1x) stay as they were.
- A row rounded below the font's height: text is centred in its row (gpui-pre's `ShapedLine::paint`, the same centring as Ghostty's baseline), so glyphs that reach the font's ascent or descent overhang equally above and below, at most a quarter of a device pixel each at `line_height` 1 (a `line_height` below 1 overhangs by design, either way). Small sizes can put the text underline (gpui-pre draws it at 0.618 of the descent below the baseline) a fraction of a pixel into the next row, drawn over its background rather than cut. Program backgrounds paint before any text, so they don't cover the overhang; the cursor, the input method's composing background and images drawn above text can, by that quarter pixel. Box and block sprites, Nerd icons and fallback symbols are sized from the cell itself, so they fit whatever it rounds to.
- Settings window: a "Cell rounding" choice (Outward / Nearest) under "Cell width".
- Tests: `terminal::tests::{nearest_rounding_keeps_the_grid_within_half_a_device_pixel, cells_follow_each_fonts_metrics_by_the_rounding_rule, nearest_keeps_twelve_point_and_meets_ghostty_when_zoomed, a_shorter_row_overhangs_a_quarter_pixel_each_side_at_most, cell_rounding_applies_live, pixel_cell_width_rounds_after_letter_spacing, line_height_stays_within_its_range}`, `settings::tests::cell_rounding_defaults_to_outward`. The font tests use CoreText directly (macOS only); the test window's text system gives every font the same metrics.

### Settings search

`feat/settings-search` (branched from `master`, fork only): a search field at the top of the Settings window's sidebar. It finds a setting by its name, its description or the settings.json key it writes, and filters every page in place to its matches.

- Results: every page with a match shows under its own title (a click opens the page), with only its matching settings under their section headings, controls working as on the page. Filtering in place rather than a list that jumps to a row: the setting can be changed right in the results, and a list would need a scroll-to-row the mod API (application programming interface) lacks. Notes and spacing between settings are left out of results. With no match it says "No settings match".
- Matching (`searchWords`, `wordSpan`, `matchSetting` in `defaults/frame/settings/main.js`): case-insensitive, with settings.json's `_ - .` read as spaces, so `cell_rounding`, "cell rounding" and "rounding" all find Cell rounding. Every typed word must fall in the setting's title, keys, description or section heading, as a prefix or a substring. Titles and keys also forgive one typo (a letter added, dropped, changed or two swapped) in a whole word of four letters or more that starts with the same letter, so "roundng" finds Cell rounding and "sound" doesn't find "round". Descriptions only match as typed, since a typo there finds too much. The palette's matcher (a word's letters in order anywhere in the text) is looser than a filter of settings wants.
- Marks: matched text is tinted (background only, no weight change, so nothing moves while typing). Results show each setting's settings.json keys under its name, marked where they matched. A description has its matches marked too, drawn a word at a piece so it still wraps.
- Keys: cmd-f (ctrl-f off macOS) focuses the field and selects its text. Typing a character with nothing focused that takes keys (no field, font list or rename open) starts a search with it; a lone space doesn't. Esc clears the words (and closes a font list or rename opened in the results, whose page isn't the one shown after), then leaves the field, and only then does its usual job (closes a font list, then the window). Off macOS an Alt key is a shortcut, not a character to search for. A click on a page in the sidebar leaves the search.
- Index: each page's rows record their title, description, keys and heading through `row()` and `block()` (pickers and lists that are settings: Layout, Dark and Light theme, Option key, each machine, Add a machine). The index is built the first time a search runs, by one pass over the pages, which also starts reading the machine list and the layout file if their pages haven't yet. It's built again only when what the pages draw from changes (`settings()`, `updates()`, `telemetry()`, `layoutSpacing()`, settings.json, the machine list, the layout file and its name), so a description that changes, such as an update check's, or a row that appears is found as it reads at that moment; a keystroke matches the words against the index and draws the pages with only their matches. A row drawn that the index lacks is matched as it draws and indexed next time. With the field empty none of this runs: `row()` returns at its first check, and the pages draw as they would without the search field.
- Perf: not benchmarked. The index pass runs each page's builder once; a keystroke runs `matchSetting` once per indexed row and draws the matching pages, which is the same element-building work as showing a page.
- Tests: `scripts/settings.test.ts` (word folding, prefix and substring and typo matching, every word required, marked runs, only matches shown under page and heading, finding by key and with a typo, the no-match state, the index built once and again after a write, a page not yet opened read in, a changed description found, nothing indexed with the field empty, cmd-f, typing into the field left to it, esc and alt), `mods::render_tests::settings_search_filters_every_page`.

### App icon

`feat/app-icon` (branched from `master`, fork only): `app_icon` in settings.json, a built-in variant (`"classic"`, default, `"midnight"`, `"mirage"`, `"glass"`, `"phosphor"`, `"graphite"`), `"theme"` (see Theme icon below) or an absolute or `~/` path to an `.icns`, `.png` or `.svg` (relative paths are refused: Herdr runs from `/` when the Dock starts it and the install scripts from the checkout, so one would name two files). One key rather than a "custom" value plus a path key: a path can't be mistaken for a name, since names have no `/`.

- Artwork: `scripts/app-icons.py` draws the five variants other than Classic from `assets/icons/herdr-ui-icon-clean.svg` (keeping its Apache-2.0 attribution metadata) into `assets/icons/variants/<name>.svg`, builds each `.icns` with rsvg-convert and iconutil, and renders the Settings previews (`defaults/frame/settings/app-icons/<name>.png`, 96 px). Classic is `assets/icons/Herdr.icns`, as in upstream. The SVGs (Scalable Vector Graphics files), `.icns` and previews are checked in, as `Herdr.icns` is, so builds and installs need neither tool; `--check` (run by `just test`) fails when the checked-in SVGs differ from what the script draws. Sizes up to 32 px are drawn without glows, shadows, sheens and scan lines, which blur a small icon into its tile (Phosphor's glow and Glass's sheen did); Phosphor's glow is also tighter at every size (blur 6 in the artwork's units, scan lines at 20%). Every drawn variant sits on macOS's icon grid as the system draws other apps' icons (measured from macOS 27's own renderings of Terminal, Notes, Ghostty and Rex): an 824 px tile with 100 px margins on the 1024 canvas at every size, corners that are superellipse quarters (radius 256, exponent 2.5, within a pixel of the system's mask), and the system's drop shadow (black at 25%, blur 16, 8 down, a blurred copy of the tile rather than `feDropShadow`, so Linux renderers and AppKit's CoreSVG draw it too) baked into the margin. The artwork keeps its own 896 px tile and is scaled onto the grid (0.92). The shadow has to be in the image: `setApplicationIconImage` hands it to the Dock and app switcher as it is, while Finder's bundle icon is masked and shadowed by the system either way, so it looks the same with or without one. Classic is upstream's `Herdr.icns`, unchanged: on the grid at 64 px and above, but its 32 px images are 28 px tiles (Apple's are 26) and it has no shadow. Settings previews classic from that `.icns` (sips) so the six tiles share one size.
- Runtime (macOS): `app_icon::follow`, called from `settings::set`, hands the image to `NSApplication.setApplicationIconImage` at start-up and whenever the setting changes, from bytes built into the binary (about 1.5 MB for the five), so any build shows them. Off the main thread it does nothing. It remembers an icon only once AppKit took it, so a file that can't be read or decoded logs a warning, leaves the Dock as it was and is tried again with the next settings. ### Font thickening

`feat/font-thicken`, then `feat/font-thicken-setting` (the upstream pull request's branch, merged over it): `font_thicken` (`"auto"`, `true` or `false`) and `font_thicken_strength` (0 to 255, default 255), person settings for how terminal glyphs rasterise. `"auto"` (absent, the default) is GPUI's own: it picks the smoothing level from the text color's luminance, so dark text on light draws at the lightest level and light text on dark at the heaviest. `true` draws as Ghostty's `font-thicken` does: CoreGraphics font smoothing on, a gray fill of strength / 255 in linear gray, whatever the text color, then tinted. `false` draws as Ghostty's `font-thicken = false`: smoothing off (`setShouldSmoothFonts(false)`), plain antialiased coverage, the same for every color. `true` and `false` are JSON booleans; the app never wrote `false` (the toggle removed the key), so `true` and an absent key mean what they did, and a `false` written by hand or by an agent turns smoothing off rather than drawing as the default; any other string is a `problems()` entry and draws as `"auto"` (`settings::Thicken`, which keeps it to name). `ui_font_thicken` and `ui_font_thicken_strength` (same values and defaults) do the same for every other glyph in the window: panels, tabs, overlays, toasts, every mod and the Settings window. `HERDR:` changes in `vendor/gpui-pre` (`GlyphThicken`: `Auto`, `Strength(u8)` or `Off`, in `RenderGlyphParams::thicken` and so in the glyph atlas key; `Window::with_glyph_thicken`) and `vendor/gpui-pre-macos/src/text_system.rs` (the rasteriser, and 1 more pixel of raster room for `Strength`, as Ghostty pads thickened glyphs). `Window::set_glyph_thicken` sets the thickening each frame's paint starts at, deferred draws and tooltips included; `AppWindow::render` sets it from `ui_font_thicken` (`Settings::ui_glyph_thicken`), beside `set_rem_size`. ### Text contrast

`feat/text-contrast`: `text_contrast` and `ui_text_contrast` (0 to 1, default 0), person settings that sharpen glyph edges when they're blended, without widening the strokes. The monochrome-sprite fragment shader moves the glyph's coverage toward smoothstep by the setting: `alpha' = mix(alpha, alpha² (3 − 2 alpha), contrast)`. The curve is symmetric about 0.5, so faint edge pixels fade, nearly solid ones fill, and a stroke keeps its ink. GPUI's wgpu and DirectX backends already apply Zed's DirectWrite-style `enhance_contrast`, `alpha (k + 1) / (alpha k + 1)`, with a global, luminance-scaled `k` and a gamma correction. The Metal backend has no curve. Zed's curve is not reused here: it raises every partial pixel, so it adds ink as thickening does. Measured on Metal at k = 1, it added 14% ink to light on dark and 17% to dark on light. Its luminance factor is 0 for light text, so it would leave light-on-dark terminal text unchanged. The wgpu and DirectX backends apply the S-curve after their own correction, so 0 leaves every backend as it was.

`HERDR:` changes are in `vendor/gpui-pre/src/scene.rs` and its cbindgen copy `vendor/gpui-pre-apple/vendor/gpui/src/scene.rs`. They add `MonochromeSprite::contrast` and an 8-byte-aligning `contrast_pad`, making the sprite 30 words. They are also in `vendor/gpui-pre/src/window.rs` (`with_glyph_contrast`, `set_glyph_contrast`, and `paint_glyph` stamping the sprite), and in the `sharpen_coverage` function in `vendor/gpui-pre-apple/src/shaders.metal`, `vendor/gpui-pre-wgpu/src/shaders.wgsl` and `vendor/gpui-pre-windows/src/shaders.hlsl`. The WebGL decoder reads 30 words. On DirectX, subpixel sprites read their own `SubpixelSprite` buffer, which has no `contrast`, instead of `MonochromeSprite`'s. Contrast is applied at blend time, so it isn't in the glyph atlas key: interface and terminal glyphs share tiles. SVG icons draw at 0. `AppWindow::render` sets the window's contrast from `ui_text_contrast`, beside `set_glyph_thicken`. The terminal paints its grid inside `with_glyph_contrast(text_contrast)`. The row cache keeps shaped lines, not sprites, and re-reads the contrast each paint, so `painted_with` doesn't carry it.

- Measured (`tests/text_contrast.rs`, JetBrains Mono at 12 device px, headless Metal). Edge share is the share of inked pixels with coverage between 0.2 and 0.8, and ink is the mean coverage over the text's box:

| Text | Contrast 0 | 0.5 | 1 | Ink at 0 → 1 |
| --- | --- | --- | --- | --- |
| Light on dark | 0.440 | 0.390 | 0.360 | 0.0711 → 0.0719 (+1.1%) |
| Dark on light | 0.503 | 0.433 | 0.374 | 0.0588 → 0.0590 (+0.3%) |

- For comparison, `font_thicken` 255 takes dark-on-light ink to 0.0711 (+21%). `ui_text_contrast` 1 takes the panels' edge share from 0.440 to 0.360, while a terminal grid inside it at 0 stays at 0.440.
- Settings window, Text > Rendering page: under Interface text, an "Interface contrast" stepper; under Terminal text, a "Contrast" stepper below Thicken. Both step by 0.1 within 0 to 1. At 0, the key is left out of settings.json. Layouts set neither.

### Automatic pane names

`feat/pane-auto-names` (branched from `master`, fork only): with `pane_auto_names` on, a pane at a bare shell that nobody named shows two calm words of its own, such as "hazy-inlet", in the flavour of Rex's session names, instead of the shell's name. Shells all read "zsh", so a split of three shells had nothing to tell them apart by until someone renamed them; a stable name gives each one an identity for free.

- Precedence: the person's `pane.rename` name, then an agent or a running command, and the automatic name only at a bare shell whose title says nothing: empty, the terminal's address (its title before the shell sets one), the shell's name (`zsh`, `-zsh`, `/bin/zsh`), or only a folder (`~/src`, `/tmp`, `C:\src`, the cwd or its last part, any of those after `user@host:`). Decided once in Rust (`pane_names::shown`, which knows the shell list in `programs.json`), so every mod gets the same answer: `panes()[i].auto_name` is the name when the pane should show it and null otherwise (always null with the setting off, and for mod panes). The shipped `pane` and `terminals-pane` headers read `label` (see Pane and agent labels), where `auto_name` comes second.
- Stable: 64-bit FNV-1a (Fowler–Noll–Vo hash) over the pane id's bytes (fixed, unlike std's per-process SipHash keys), modulo adjectives × nouns. Two panes of one tab that land on the same name: the one whose id sorts later takes the next index in the list. Pane-id order rather than tree order, since pane ids are random and stable while a pane's place in the tree changes when panes move. Every pane of the tab takes part, whether it shows its name or not, so a neighbour starting an agent never moves another pane's name. The same layout gives the same names after a restart. Known limit, accepted: a new split whose id sorts earlier and lands on an existing pane's name takes it, and the existing pane's header shows the next name until that split closes (rare: about 1 in 2,304 per extra pane in a tab). Keeping first-come names would need per-pane state that survives restarts, which the display-only design avoids.
- Display only: never written into the layout or settings.json. `pane.rename`'s prompt starts from the automatic name (hint "empty: its automatic name"), so Enter keeps it as the pane's real name.
- Words: `defaults/pane-names.json` (`{"adjectives": [...], "nouns": [...]}`, 48 × 48, three to seven letters, landscape, weather and light, British spelling, nothing that reads as slang, as a judgement, or as a pane's state next to a status dot), embedded with `include_str!` and checked once when first read (non-empty lists, lower-case words, no duplicates); a file that fails disables the names with a warning rather than crashing. Our own list: Rex's (seen only as strings in its binary, licence unknown) set the flavour, none of its words are reused, the test fixtures included.
- Setting: `pane_auto_names` in settings.json, off by default (left out of the file when off); Settings > Appearance > Panes, "Name panes automatically". Turning it on or off republishes `panes()` at once.
- Perf: nothing in the paint path. The names are worked out in `publish()`, which runs on model changes and title changes, never per frame: one FNV pass over each pane id and a small map per tab. The header mods only read a string from `panes()`. The window keeps the shown names by pane (`auto_names`) for the rename prompt.

### Tab reordering

`feat/tab-reorder` (branched from `master`, fork only): tabs reorder by dragging, from their menu and by keys. The shipped `tabs` mod moved a tab only when a press on one tab was released over another, with nothing on screen while it happened, and a release in a gap or past the last tab did nothing.

- Drag: a press on a tab becomes a drag once the pointer moves more than 4 px (`DRAG_THRESHOLD`); a click without that movement still selects (on release over the tab it was pressed on) and a double click still renames. While dragging, the tab dims in its place, a copy of it (the ghost) follows the pointer across the strip, kept where it was grabbed, and a 2 px accent line marks the gap it will land in. Dropping anywhere on the strip moves it there: over a tab, its left half means before it and its right half after; the gaps keep the last place; the strip's padding left of the first tab means first; the empty space after the last tab, the buttons and anything right of it mean last. No line shows where nothing would change. Escape or the pointer leaving the strip cancels; the release after that does nothing. A release the strip never heard ends the drag too: the next move without the left button held, or the next press.
- How: gpui-kit's drag support is the dock's (`drag_tab`), which this strip isn't, so the mod tracks `on_mouse_move` on each tab (its half, from `local_position` against `bounds`), on a `tab-tail` spacer after the tabs, on the `tab-scroll` row (its bounds) and on the strip root (left of the row: first; right of it: last). There is no `on_mouse_up_out`, so leaving the strip (`on_hover(false)`) is what cancels a drag released outside it; a mouse move's `pressed_button` (a `HERDR:` change in gpui-kit's `dispatch_mouse_move`, `vendor/gpui-kit/crates/shell/src/engine/quickjs/mod.rs`, typed in `typings.rs`) ends one whose release went missing. Esc needs the keyboard: a drag focuses the strip's own handle, and `pane.refocus` gives it back to what has the focus, as closing a popup does (`restore_focus`): a focused mod pane gets its `focus` command again, else the focused pane, or the agent shown, without changing what it shows (`pane.focus` would end a swapped-in sub-agent and reset the agent shown; hidden from the palette). The wheel doesn't switch tabs during a drag. `slotOver` and `dropIndex` are the pure halves (exported for the tests).
- Menu: the tab menu has Move left and Move right after Rename, each hidden at its end.
- Keys: `tab.move_left {id?}` and `tab.move_right {id?}` move a tab (default: the shown one) one place; at the end nothing happens. Defaults: Cmd+Shift+Left / Cmd+Shift+Right on macOS (Cmd+Shift+[ / ] already switch tabs; gpui-kit's text inputs keep Cmd+Shift+Left / Right for selecting, their context binding winning), no default elsewhere: Alt+Shift+[ / ] are Meta-{ / Meta-} to terminal programs (emacs and readline paragraph moves, bash's `complete-into-braces`), and GPUI may report the key as `{`, which would never match. `src/keys/shipped/fork-0990622-keys{,.macos}.json` are the defaults before the macOS keys, so untouched keys.json files gain them; `fork-1225b24-keys.json` is the Linux and Windows file that had Alt+Shift+[ / ], so an untouched one loses them; edited ones keep theirs.
- `tab.move` lives in `Model::move_tab`, which fails on a pane id instead of panicking on it.
- Tests: `model::tests::tabs_move_to_a_place_or_one_step_and_stop_at_the_ends`, `window::tests::{pane_text_zoom (pane.refocus keeps a swapped-in terminal), pane_refocus_hands_a_focused_mod_block_its_keyboard_back}`, `keys::tests::untouched_fork_keys_give_alt_shift_brackets_back_to_programs`, `mods::render_tests::tabs_draw_a_drag_in_progress`, `scripts/tabs.test.ts` (slot halves, drop index for every slot, click versus drag, gaps and both ends, Escape and leaving cancel, a lost release, a tab closed mid-drag, menu moves hidden at the ends).

### Toasts stand out, and go where you put them

`feat/toast-look` (branched from `master`, fork only): on `popover` with the panel `border`, toasts were barely apart from the window on many themes (ayu-mirage: surface 1.16:1 and border 1.43:1 on the background; ayu-light: 1.00:1 and 1.14:1), so they were easy to miss. They draw from their own colors, computed once in `settings::resolve` each time the theme resolves (`toast_colors`), never per toast or per frame. The colors are `toast` (the surface), `toast_border`, `toast_shadow`, `toast_foreground`, `toast_muted`, and a level stripe and dot color per level (`toast_info`, `toast_success`, `toast_warning`, `toast_error`). Each is the smallest step that holds a measurable floor:

- **Surface:** on a dark theme, at least 1.3:1 on `background` (`TOAST_LIFT`), stepped toward the terminal's foreground, else white. On a light theme it is white: a white background can't show a lighter surface, so the border and shadow carry it there.
- **Border:** at least 1.7:1 on the background (`TOAST_EDGE`) and 1.25:1 on the surface (`TOAST_SEAM`).
- **Title and body:** at least 4.5:1 on the surface (`TOAST_TEXT`).
- **Level stripe and dot:** at least 3:1 on the surface (`TOAST_MARK`), from `accent`, `done`, `working` and `blocked`.
- **Shadow:** two layers, deeper on dark themes.
- **Overrides:** a theme's or settings.json's own `toast*` colors win, and the rest are held to the `toast` actually drawn. A theme that paints its own panels (Win98) keeps its `popover` and `border` where they hold the floors.
- **Translucent values:** a `#rrggbbaa` value counts as drawn, composited over the background (the toast) or over the toast (everything else), in `toast_colors` and in the `toast_problems` check (`drawn_over`).
- **Results:** ayu-mirage goes to 1.32:1 (surface) and 1.75:1 (border); ayu-light to 1.05:1 and 1.74:1. Every preset, shipped file, public extreme and installed Rex theme holds every floor.

`toast_position` in settings.json (`bottom-right` default, `bottom-left`, `bottom-center`, `top-right`, `top-left`, `top-center`) places the stack, and the core-update notice follows it.

- **Stacking:** bottom stacks grow up with the oldest nearest the edge. Top stacks grow down with the newest nearest the edge.
- **Top chrome:** a top stack starts 16 px below the window's top chrome: the system title strip (where the layout's root starts) plus the lowest `window_drag` bar along the top, as painted. The bounds canvases every layout node already has record it (`top_chrome`, `AppWindow::top_chrome`), so no tree walk runs per render. Bars stacked along the top (a tab bar under a title bar) count, each starting where the chrome so far ends. Only the main layout's nodes count, not an overlay's. While a top toast shows, an O(1) probe, drawn last, asks for one more frame (`on_next_frame`; `refresh` is ignored while painting) if this frame painted a different chrome (zoom, a bar shown or hidden).
- **Offset range:** each of `toast_offset`'s values is kept within -16 to 400 px (`TOAST_OFFSET`), and a value outside is reported as a settings problem.
- **Offset:** `toast_offset {x, y}` moves the stack in from the side and from its edge. The whole stack moves together (`toast_start` clamps once, at the edge), and never under the update pill. The pill is reserved for right and centre stacks only.
- **Settings window:** "Notification position" (Rex's label) on Appearance > Window, a small window of six places in its top row and bottom row, the chosen one the tonal pill.

### Toast time, style, corners and level mark

`feat/toast-prefs` (branched from `master`, fork only: it builds on "Toasts stand out, and go where you put them" and "Toasts coalesced and capped"): four settings.json keys, each left out when it holds today's look, so a settings.json without them draws toasts exactly as before.

- **`toast_duration`** (`short`, `normal` default, `long`, `until-dismissed`): scales the level's own time (5 s, or 8 s for errors and warnings, which include "needs you" alerts) by 0.6, 1 or 2, or keeps the toast until clicked. A `timeout` the poster set wins unscaled: the caller chose it, and that keeps the 1.5 s "Copied" brief. Until clicked doesn't pile toasts up or starve new ones: past five, `close_toasts_past_limit` closes the oldest routine toast, else the oldest error or warning, but never the one just opened, so a "Copied" after five kept errors still shows. A toast already open keeps the time it opened with. The core-update notice already stays until an update goes through. Expiry is still the `expires` instant the window's 400 ms poll checks (`toast_timeout`, now `Option`), set when a toast opens or an alert joins it, so nothing new runs per frame, and the mod roots' toast clock (upstream #548) is a different, gpui-kit toast that this doesn't touch.
- **`toast_style`** (`standard` default, `subtle`, `high-contrast`, `accent`): a set of floors (`ToastFloors`) and a starting surface for `toast_colors`, which still runs once per theme resolve, never per frame. Standard is the derivation as it was, value for value (`tests/fixtures/master-toasts.json`, from `master`). Subtle starts from the panels' `popover` where it lifts 1.12:1 off a dark background, with a border at 1.35:1 and 1.1:1 and a lighter shadow. High contrast holds the border at 3:1 on the background and 2:1 on the toast, text at 7:1 (WCAG AAA (Web Content Accessibility Guidelines, enhanced level)) and marks at 4.5:1, with a deeper shadow; it doesn't start from a theme's own `popover` (a mid-grey one, `#6b6b6b` on a dark theme, tops out near 5.3:1), and under a `toast` colour the person set it holds 7:1 where that surface allows. Accent mixes the theme's `accent` into the surface (18% dark, 10% light) and lifts it again if that sank it. Every style keeps text at 4.5:1 and marks at 3:1 or more. A theme's or settings.json's own `toast*` colors still win, and a theme that paints its own panels (Win98) keeps its popover, except under high contrast.
- **`toast_corners`** (`square` 0 px, `slight` 4 px, `rounded` 8 px default): the radius `toast_frame` draws, for mod toasts and the core-update notice alike. Herdr draws the toast's box, so this stays in Rust beside the surface and border.
- **`toast_mark`** (`stripe` default, `dot`, `none`): the level mark. The toast mod draws the stripe and dot, so the choice reaches it as `props().toast_mark`, which `open_overlay` and `join_alert_toast` put in every toast's props (`with_toast_mark`), so a toast's render reads no settings; a replacement toast mod reads it the same way. The core-update notice in Rust follows it. Stripe and dot keep their 3:1 floor (4.5:1 under high contrast). With `none` the level shows only in the wording ("needs you", "failed"): coloured titles would need a fourth set of level colours held to 4.5:1 for a look the person picked to be plain.
- **Separate keys, not one preset:** corners and marks are shape and the style is colour, so each reads as one small picker and switching the style never changes a shape someone chose.
- **Settings window:** on Appearance > Window under "Notification position": "Notification time" (Short, Normal, Long, Until clicked), "Notification style" (each style drawn as a small toast in the current theme's colours for that style, with the chosen corners and mark, from `toastLooks()`: each style's colours and each corner radius, resolved once per `settings::set` and read only by the Settings window, so the `settings()` every mod reads carries none of it), "Notification corners" and "Notification level mark". Each applies live: colours and corners redraw every open toast on the next frame; the mark and the time apply to toasts opened from then on, and open ones keep theirs.
- **Bad values:** like `toast_position`, a value outside the list fails settings.json, which the settings problems report.
- **Upstream's three questions:** (1) Does the app act on it? Duration yes: the window decides when a toast expires, and the toast clock is the window's. Style, corners and marks no: they only change how toasts look. (2) Can only the app see it? Duration yes (expiry is the window's poll); the colours are derived in Rust today, but a mod could compute them from `theme()`. (3) Can a mod not do it? A mod can't change when Herdr's own toasts expire, so duration is a core setting; the toast mod can draw any mark (it already gets `toast_mark` in its props) and a mod could restyle colours with `frame: "none"`, so style, corners and mark bend the rule the way "Toasts stand out" already does. Verdict: duration C (ask Can, with an issue first); style, corners and mark D (fork only, rule-bending like `toast_colors`).

### Popup command

`feat/popup-command` (branched from `master`, fork only): `terminal.popup {argv, cwd?, hold?, wait?, width?, height?}` starts a program on this computer as `hc run --bg --no-parent` does (`rm` unless `wait`) and opens the `terminal.peek` overlay for it in the same step, so there is no retry while the window learns about the terminal. `herdr-app popup [--cwd DIR] [--hold] [--wait] [--size WxH] [--] cmd args…` drives it over the control socket; with `--wait` it sends `{"wait": terminal}`, which the window answers from the core's events once the terminal finishes, then removes the terminal, and the CLI (command-line interface) exits with its exit code, 128 + the signal for a program a signal killed (the core's `signal`), or 1 (removed before it ended, the window is not open or the popup failed). The popup's ✕ and backdrop only hide it and the program keeps running: `POPUP_CLOSE_ENDS_PROGRAM` in `src/window.rs` flips that, through the peek bar's `close_ends_program` prop. A new popup ends the program the last `terminal.popup` started, whether that popup is open or hidden (`popped` tracks it, with the core's `created_ms`, until it is ended or a listing shows it finished, gone or another terminal at its address, since addresses come back after a core restart; a wait popup's terminal stays until its waiter has the exit code). A `terminal.peek` of an existing terminal is never ended, and a plain `terminal.peek`, such as a link clicked in a popup, ends nothing: it only hides an open popup, which the next popup still ends. It replaces the logic of the `herdr-popup` shell script in dotfiles, which is a wrapper over it.

- `--hold` reads one key with `stty` and `dd`, which any `sh` has (dash, Linux's `/bin/sh`, has no `read -n`).
- Timeouts: the control server gives `terminal.popup` 15 s (`POPUP_ANSWER_WITHIN`), past the 10 s `Core::call` may take for `terminal.run` on the UI thread, and the CLI waits 2 s longer. If the CLI gives up anyway, the reply channel is gone when the window answers, and the window ends and removes the wait popup (`abandon_popup`) instead of keeping it.
- While a request waits, the server checks its stream for a hang-up every 500 ms (`await_reply`, `hung_up`): Ctrl-C on `--wait` drops the waiter, and the program keeps running. On Unix a hang-up is `POLLHUP` (asked for with `POLLOUT`, which macOS needs to report it), so a client that only shut its writing half after the line (`printf … | nc -U`) is still waited for and gets its answer. A finished wait popup nobody has asked about keeps its answer and its terminal for `WAIT_KEPT` (60 s), then both go (`expire_waits`); closing or quitting the window removes the finished ones (`rm_finished_waits`).
- `--size`: a side up to 1 is a fraction of the window and one from 50 is px; between them (`1.5`) is a usage error, more likely a mistyped fraction than a tiny popup.

### System notifications

`feat/system-notifications` (branched from `master`, fork only): an agent alert ("<name> needs you", "<name> hit an error", "<name> finished") also goes to the system's notification center through GPUI's `show_system_notification`, titled as the toast with the agent's own message (its 7501 `msg`, when it gave one) above "space / tab" as the body and tagged `herdr-agent:<address>`, so a newer alert for the same agent replaces the older one. `system_notifications` in settings.json says when: `background` (default; only while Herdr's window isn't key), `always`, or `off`; never while the person is looking at that agent (`alert::should_notify`). Clicking one activates Herdr and runs `agent.focus` for it, as the toast does; it is dismissed once the agent is looked at, starts working again or goes away, except a "needs you" one, which stays until the agent is no longer blocked (below). `dock_bounce: true` calls `request_attention` for "needs you" while Herdr is in the background. `alert_command` (a string run by `/bin/sh -c`, or an argv array) runs fire-and-forget in place of the system notification, under the same rule, with `HERDR_AGENT_STATE` (blocked|error|done), `HERDR_AGENT_PREV_STATE`, `HERDR_AGENT_APP`, `HERDR_AGENT_NAME`, `HERDR_AGENT_ADDRESS`, `HERDR_AGENT_PLACE`, `HERDR_ALERT_TITLE`, and the agent's own 7501 words as given (`HERDR_AGENT_MESSAGE` from `msg`, `HERDR_AGENT_KIND` from `kind`, `HERDR_AGENT_TITLE` from `title`; empty when absent, read from the terminal's record in the core's listing by `alert::Said::of`), so the herdr TUI's (text user interface's) and tuios's `notify` adapters have a Herdr counterpart. The vendored GPUI posts nothing unless the app runs from a bundle (its `NSInternalInconsistencyException` guard), so dev builds stay silent. Settings window: a "System notifications" choice and a "Bounce the Dock icon" toggle under Alerts.

- An `alert_command` starts in the home folder (the app's own is `/` when opened from the Finder) and in its own process group; still running after 30 s, the whole group is killed (`alert::reap`), so a hung one doesn't keep its thread and programs forever. One that doesn't start posts the system notification instead (`alert::Sent::Fallback`), and an error toast says why, once per distinct reason (`alert_command_errors`, cleared when a settings reload changes `alert_command`). A shell line always starts, so a missing program only shows as exit 127: one that started returns `alert::Sent::Ran` with a channel on which the reaper thread sends why a non-zero exit failed (`alert::exit_failure`), and the window then posts the system notification and the same once-per-reason toast. One killed by a signal is only logged at warn level.
- Sticky "needs you" (`notification_sticky`, on by default; settings.json only): `alert::Notified` records each posted agent notification with its alert, and `Notified::withdraw`, run on every listing in `tend_terminals`, decides when it comes down. ### Rows kept while output scrolls

### Hidden terminals free their drawing caches

`perf/hidden-caches` (branched from `master`, fork only): a terminal off screen for a few seconds frees what drawing kept for it. Every tab's terminals stay attached (instant switches, kitty images), and each one ever drawn held libghostty's render state (its row cache) and the app's `Cell` rows and row drawings: ~2.4 MB of heap per terminal at the bench's window size. A drawn terminal checks every `HIDDEN_CHECK` (2 s) whether the window's last frame showed it (`shown_in`, the signal off-screen output already uses); off screen for two checks in a row (2 to 4 s), `TerminalView::release_frame_caches` drops the row drawings and `Vt::release_frame_caches` frees the render state and makes a new one (libghostty has no reset call) and forgets the rows read from it, then the check stops until the terminal is drawn again, which reads the whole screen as a tab switch already did. Quick flips keep everything. The screen, scrollback, selection, scroll position and kitty images stay. A synchronized update in progress keeps its held frame (no release then), and a released terminal doesn't fill the render state for one. `Vt::new` frees the state it filled to read the default colors, so terminals attached in hidden tabs (all of them after a restart) hold none until drawn.

Worst frame in the second after a tab switch p50 22–25 ms either way, also into a released tab (22–24 ms); steady streaming CPU (central processing unit) unchanged (311–318 vs 335 M instructions/s).

### Spinners turn without a draw

`perf/spinner-repaint-only` (branched from `master`, fork only): a mod's `svg(...).spin(ms)` turns with no render, layout or paint of anything, its view's or the window's. GPUI marks every ancestor of a notified view dirty and renders the root view on every draw, so the 100 ms wake gpui-kit's `spin_layer` gave its ShellRoot ran `AppWindow::render` and the whole window's prepaint and paint per step (the bench's `idle-busy-bg`: ~8 window draws a second with no terminal drawn). GPUI has spinning sprites: `Svg::spinning(period)` / `Window::paint_spinning_svg` paint a monochrome sprite whose `pad` slot (which no shader reads) holds its period, so a cached view replaying the sprite replays the spin. `Window::present` turns every spinning sprite of the frame on screen to `gpui::spin_clock_ms()`, and while that frame has one, a timer asks for a present-only frame every `SPIN_STEP` (100 ms, ~10 fps) through the platform's frame source. gpui-kit's `spin` draws such an svg in place, so the hosted spinner layer (`Spin`, `spin_layer`, `build_view`, `Fade` and the inline fallbacks) is gone, and a spinner keeps its true stacking, opacity and clipping. A spinner turns about its drawn sprite's center (within a device pixel of its element's center).

- A step already scheduled when a draw took the spinners away presents nothing; steps wait while the window is hidden (`Window::visibility`) and start again when it is visible.
- `Scene` keeps `has_spinners`, set when a spinning sprite is inserted (cached replay inserts too) and cleared with the scene, so a present without spinners skips the scan.
- `Svg::spinning` works for an `external_path` or inline data svg as well as a `path` one.
- A spinner drawn fully transparent (opacity or colour alpha 0) is left out of the frame, so it doesn't keep the window presenting. `spin(ms)` ignores a non-finite `ms` and clamps the rest to 100 ms – 1 hour; the gpui-kit tests sit outside the workspace, so a root-crate test (`spin_with_an_absurd_period_draws_without_panicking`) hands Infinity, NaN and 1e300 to `spin` through the script bridge (`__apply`; `.spin()` itself rejects them in JavaScript) and renders.
- The turn is not reflected in the sprite's bounds for layer ordering and clipping, so a spinner should be round or symmetric within its box.

- Files: `vendor/gpui-pre/src/scene.rs` (`MonochromeSprite::spins`, `turn`, `Scene::turn_spinners`, `has_spinners`), `vendor/gpui-pre/src/window.rs` (`SPIN_STEP`, `spin_clock_ms`, `paint_spinning_svg`, `present`, `schedule_spin_step`, `refresh_visibility`, `presented_spinners`, `presents`), `vendor/gpui-pre/src/elements/svg.rs` (`Svg::spinning`), `vendor/gpui-pre/src/app/test_context.rs` (`set_asset_source`, `simulate_window_frame_request`), `vendor/gpui-kit/crates/shell/src/materialize.rs`, `vendor/gpui-kit/crates/shell/src/root.rs`, `vendor/gpui-kit/crates/shell/src/view.rs`, `vendor/gpui-kit/crates/shell/src/typings.rs`, `src/window.rs` (comment), `src/mods/lifecycle_tests.rs` (test `spinners_turn_without_drawing_the_window`)

### Interface zoom and text size

`feat/ui-zoom-text-scale` (branched from `master`, fork only): two settings.json scales for the panels, both default 1, where 1 draws exactly as `zoom` alone. `ui_zoom` (0.75 to 1.5) scales the layout's px sizes, pane headers, tabs, overlays, popups, toasts and every mod's px on top of `zoom`; terminals keep their font, cells, letter spacing and padding at `zoom` alone. `ui_text_scale` (0.8 to 1.3) multiplies only text: Herdr's panel text (`settings::zt`, `settings::text_rems` for what was `text_xs`, and the window root's text size), and mods' `text_size(...)` (px or `"1rem"`), the reflected `text_xs()` … `text_3xl()`, px and rem `line_height`s, editor `font_size`, mod tooltips and the shell's failure banner through a `HERDR:` text scale in gpui-kit's bridge (`set_text_scale`, `scaled_text_px`, `scaled_text_rems`, `style::text_length`, `style::apply_nullary`, `style::line_height`). The window's rem (`settings::ui_rem`) is the base text size at `zoom × ui_zoom` without the text scale, so rem spacing, radii and gpui-kit's own panels keep their size. `zoom × ui_zoom` stops at the largest zoom (3). Both are clamped when settings.json is read, reported by `Settings::problems()` when out of range (`asked_ui_scales`), and apply live like the other settings. Mods get `settings().ui_scale` (`zoom × ui_zoom`, capped) and `settings().ui_scale_ranges` (`Settings::for_mods`); mods that turn window px back into their own (`tabs`, `picker`, Herdr 98's `kit.js` and taskbar, What's New) divide by `ui_scale`; Herdr 98's terminal font stays on `zoom`. Rust chrome that used rem spacing (`p_2`, `px_3`, the exit badge) uses `z()` instead, so text scale leaves its spacing alone.

### Pane arrangements

`feat/pane-arrange` and `feat/auto-arrange` (branched from `master`, fork only): `pane.arrange {mode, tab?}` rebuilds a tab's existing panes (default: the shown tab) into a preset shape with even sizes, as tmux's `select-layout` and tuios's tiling modes do. Modes: `tiled` (grid, `ceil(sqrt(n))` across, row by row, a short last row's panes widen: tmux's tiled), `bsp` (dwindle: each pane takes half of what's left, splitting right, down, right…), `master` (the focused pane on the left half, the rest stacked on the right), `columns`, `rows`, `next` (the mode after the tab's last one, from `tiled`) and `off` (below). Panes keep their block whole (id, terminal or mod, name), so nothing restarts; only the row/column containers are new, and the tree is saved and synced like a manual split. Order is reading order (by top edge, then left edge, from the current sizes), which every mode's output preserves, so cycling never shuffles panes except that `master` moves the focused pane first. Focus stays; a zoomed pane unzooms. The tab's mode is this screen's choice (`TabView.arrange` in the saved view, not the shared document) and shows to mods as the tab's `arrange`. Keys: `cmd-shift-space` (macOS) and `ctrl-shift-space` (Linux, Windows) run `pane.arrange:next`; existing untouched key files get it through upstream's shipped-originals upgrade (f524898), edited ones need the line added. The palette lists "Next pane arrangement" and each mode.

- Auto-arrange: a tab keeps its mode (yabai's per-space layout), so every pane split into it or closed in it (except in `bsp`, below), by any path (`pane.split`, `pane.close`, a mod pane, a terminal kept or adopted for an agent, a program that ends), runs the mode again with even sizes. The hook is in `Model::split_tree` (used by `split_with` and by the window's initial-size guess) and `Model::remove_pane`, which own the tab's view state; a document arriving from another screen replaces the tree without them, so screens with different modes never re-arrange each other's changes. Order is the tab's reading order before the change, the new pane inserted right after the pane it split and a closed pane dropped (`arrange::arrange_in`). `bsp` keeps its tree instead (`Mode::rebuilds_on_change`), as tuios's `BSPTree.InsertWindow`/`RemoveWindow` and bspwm do: `pane.arrange bsp` builds the dwindle once, then a split halves the focused pane in the direction asked (`ctrl-b |` right, `ctrl-b -` down) as a pair of its own (`Node::split_pair`: no merging into a parent running the same way, unless the target is alone in it), so a close collapses that pair and the space goes back to the pane it was split with, and dragged sizes stay. A pane dragged to another's edge pairs up with it the same way (`Model::move_pane`). Re-running the dwindle on every split threw the requested direction away. A pane added with no direction (a terminal adopted for an agent) takes `Model::auto_axis`: across its parent (bspwm's spiral), so several in a row dwindle instead of thinning out side by side. Re-arranging never picks a master, so `master` keeps the pane in its master slot; only `pane.arrange master` makes the focused pane master. Focus and zoom are the plain split's and close's (a split focuses the new pane and unzooms). A dragged divider holds until the next split or close; `pane.swap` and pane drags keep the mode, and the next arrangement goes on in the new order. A tab holding blocks other than panes splits and closes plainly. `pane.arrange off` (palette "Arrange panes: off") clears the mode and leaves the panes where they are; `next` never picks it. `default_arrange` in settings.json (a mode name; absent or anything else: none) gives tabs made on this screen (`Model::add_tab`, `add_space`) that mode; the Settings window's Appearance > Panes page sets it ("New tabs arrange").

### Focus follows mouse

`feat/focus-follows-mouse` (branched from `master`, fork only): `focus_follows_mouse` in settings.json (default off) focuses a terminal pane, a tab's or a layout's terminal block, once the pointer rests on it for `focus_follows_mouse_delay_ms` (0 to 2000, default 150; clamped when read), through `pane.focus` as a click would. The delay is a debounce: it runs from after the pointer rests, every real move starts it over, so sweeping across a pane on the way somewhere else doesn't focus it; at 0 ms the first move onto a new pane focuses it at once. Only a real pointer move counts: content scrolling or panes moving under a still pointer, and moves under 1 px (jitter, which neither starts nor delays a wait), keep the focus. After any key down, or a focus change made some other way (menu-bound keys, clicks, mods), a wait may only start once the pointer has gone more than 4 logical px from where it was then, so a pane the keyboard focused keeps the focus while the hand rests on the mouse. It never moves while a button is held (selections, pane and divider drags, link clicks), while a dialog, popup, peek or menu is open (toasts and window overlays don't count), while Herdr isn't the active window, or onto the pane already focused; a press, the pointer leaving the pane or the window, or any of those arriving cancel the wait. `focus.toggle_follows_mouse` flips the setting in settings.json and says so in a toast. Keys pressed while it is off hold the pointer too, so a key that turns it on keeps the focus where it is until the pointer moves 4 px. `write_person` returns `PersonSaved` (saved, broken or write failed); when it isn't saved the toast is a warning, "Focus follows mouse: on (not saved: settings.json has errors)" or "… (not saved: cannot write settings.json)", and a control-socket caller gets that as an error (the zoom keys apply unsaved). The rules are a pure `Follow` state machine (`still`, `moved`, `keys`, `fire`, `cancel`) the window feeds from its root's mouse-move, mouse-exit, mouse-down and key-down listeners; the pane under the pointer is the shown terminal block (the active tab's, zoom applied, or the layout's) whose painted bounds hold the pointer, unless a floating block or a window overlay is over it there, checked again against the pointer's position when the wait ends (hidden blocks keep stale bounds and terminal hover, so neither is trusted alone).

- Settings window: a "Focus follows mouse" toggle on Input > Mouse, and a "Focus delay" stepper (50 ms steps) shown while it's on. Off and 150 ms leave their keys out of settings.json.

### Zoom in whole points

### Subpixel smoothing

`trial/subpixel` (merged into `master`, fork only): subpixel (LCD, liquid crystal display) text smoothing on macOS, off by default. `text_rendering` (terminals) and `ui_text_rendering` (panels) take `"grayscale"` (default) or `"subpixel"`; `subpixel_order` takes `"rgb"` (default) or `"bgr"`. Subpixel only draws on an opaque window on a 1x, unrotated display; on the 2x displays and anywhere else text stays grayscale, and a window moved between displays switches on its next frame. It started as a trial of the experiment listed under "Rejected text experiments" below, judged on the 1x LG display: the interface uses it there; terminal text stays grayscale, which matches Ghostty.

CoreGraphics makes no per-channel coverage on macOS 27, so subpixel glyphs are rasterised by swash. CoreText still shapes, picks glyphs and lays out advances (they match swash's to 0.00000 px). swash draws the outline at 3× horizontal resolution (`Render::transform(scale(3, 1))`) and FreeType's default 5-tap filter, [8, 77, 86, 77, 8]/256, turns each pixel's three subpixels into red, green and blue coverage (`vendor/gpui-pre-macos/src/lcd.rs`). Faces are opened once per font from the bytes Herdr embedded, a mapped single-face file, or the tables CoreText hands out (collections), at the variation CoreText draws. swash has no smoothing dilation and its plain coverage is about 17% lighter than CoreGraphics' (JetBrains Mono 12), and CoreGraphics grows glyphs more along the rows than across them. So outlines are emboldened separately across and along the rows (`Outline::embolden(x, y)`), by one growth per font (face, size in device pixels, and thicken or the color's dilation): the growth that inks a calibration set exactly like CoreGraphics' grayscale while matching each glyph's rows' ink first and its pixels second (`lcd::fit`: least squares, linear in the growth, under the ink constraint). The set is printable ASCII (American Standard Code for Information Interchange) with lowercase counted twice (evenly, Geist 13 inked 2% over grayscale on interface text; lowercase alone, 1–3% under). It is fitted once, when the font's first subpixel glyph enters the atlas (0.7–3.9 ms in a debug build, each glyph drawn by swash plain and grown 0.1 px each way at one sample per pixel in CoreGraphics' box), and cached. With `font_thicken` on, CoreGraphics draws the set at smoothing levels 0 and 4 and the growth for any level is interpolated between the two fits (`lcd::Weight`); the level is a continuous function of the strength (`lcd::thicken_level`): 0 at strength 0, through the middle of each of CoreGraphics' levels 1 to 3, to 4 at 255. CoreGraphics' own levels step at strengths 100, 165, 208 and 241, so grayscale adds no weight below 100 and jumps about 5.5% at each step, where subpixel adds some at every strength and lands within three quarters of a step of grayscale everywhere. With it `"auto"`, the fit is against grayscale at the color's dilation. With it `false`, the fit is against CoreGraphics' unsmoothed grayscale (`SubpixelMatch::Unsmoothed`, one steady growth): JetBrains Mono 12 grows −0.037 px across by 0.088 along, Geist 13 0.004 by −0.019, so swash's plain outline is nearly CoreGraphics' unsmoothed one and "off" adds no smoothing dilation. Each fit shrinks along one axis, so the move that keeps a backwards-wound glyph in place after emboldening follows the glyph's outward sign (`lcd::Glyph::outward`), not the growth's sign: a normally wound glyph grown by a negative strength stays where swash puts it. The fit, not zero growth, is kept: at zero growth the terminal line inks 2.5% under grayscale, its ascender rows 6.7% under and the x-height's top row 16.9% of the peak row under; fitted, 0.8% and 0.5% under and 8.1%. That row is where CoreGraphics' unsmoothed edges sit a little higher than swash's, which one growth for the whole font can't follow, so `check_shape` allows 9% for off (`OFF_ROW_TOLERANCE`) against 5% for auto and 4% thickened. Fitted values: JetBrains Mono 12 at strength 30, 0.073 px across by 0.117 along (0.063 by 0.115 at level 0, 0.230 by 0.150 at 4); Geist 13 at strength 192, 0.198 by 0.093. A growth fitted to each glyph (an earlier build) matched each glyph's ink and rows but gave neighbouring glyphs different stems: `i` 22% wider than `l`. swash reads one winding for a whole outline and gets some glyphs' wrong (JetBrains Mono's `i`, whose two contours its whole-outline area test reads as one backwards polygon), so a positive growth shrinks them: each glyph's sign comes from whether swash's probe growth adds ink (`lcd::Samples::outward`, cached per glyph), and it grows by the font's growth times that sign. swash grows an outline right and up, its left and bottom edges fixed; grown by a negative strength it grows left and down, so those glyphs are moved back by twice the strength to sit as the rest do. A face swash can't open falls back to its grayscale coverage. Emoji stay as they are.

Metal gains what Zed's Linux and Windows backends have: a BGRA (blue, green, red, alpha) `Subpixel` atlas kind, a `subpixel_sprite` shader pair whose second output blends each background channel toward the text color by its own coverage (dual-source blending, `MTLBlendFactor::Source1Color`), and the `SubpixelSprites` batch. Blending happens in the same gamma space as monochrome sprites, with no Zed gamma correction, so three equal coverages draw exactly as grayscale. `text_contrast` applies per channel. `SubpixelSprite`'s alignment `pad` became `contrast` (same layout; the wgpu and DirectX shaders still read it as pad). `Window::with_glyph_subpixel` / `set_glyph_subpixel` ask for subpixel glyphs under the app's platform-default mode, as the thicken and contrast pairs do; `should_use_subpixel_rendering` still requires an opaque window and `is_subpixel_rendering_supported()`, which macOS answers from the window's screen (backing scale 1, `CGDisplayRotation` 0), cached and re-checked when the screen or scale changes. `gpui::set_subpixel_bgr` swaps channels in the shader.

### Handlers inside list rows

`feat/vlist-row-handlers` (branched from `master`, fork only): a row a lazy list's item renderer returns (`v_virtual_list`, `h_virtual_list`, `uniform_list`, `list`) may register its own handlers: `on_click`, `on_hover`, `on_mouse_down`/`on_mouse_up` (any button), `on_mouse_move`, `on_action`, `on_open_change` and the rest of gpui-kit's handler methods, on the row and on anything inside it, including a `HoverCard`'s trigger and content. `cx.stop_propagation()` in a row's handler keeps the press from the list's `on_item_click`, which works too. The measuring pass's batch is never painted and is released when layout drops it, and a batch that registered nothing takes no lease and no wrapper. A handler belongs to the row it was drawn into, so a press after a scroll reaches the row that is under the pointer. Layout-phase renderers other than a list's item renderer (a dock's chrome, a registered component's element callback) still refuse handlers, with a message that doesn't point at `on_item_click`.

- Row state a handler changes (hovered, pressed, dragging) lives on the view, keyed by the list's `get_key`: a row remembers nothing between frames. A `HoverCard` in a row keeps its open state in GPUI's window state under its id, so its id must be unique per row (`card-${key}`).

### Session resume

`feat/session-resume` (branched from `master`, fork only): agents come back after a reboot. herdr-core brings kept terminals back at their addresses as fresh shells in their last folder; Herdr records, while they run, the command line that resumes each program with a `resume` rule in the programs table, and types it back into terminals that are bare shells again. - Rule: `resume` on a `programs.json` entry: `session` (`file` with `{pid}` and `~/`, `field`, `when` equalities), `drop` (flags with how many values each takes at most; a value never starts with `-`), `append` (`{session_id}`), or `{ "rerun": true }`; `{}` turns a shipped rule off. The file is read where the program runs: on this machine directly, on another through the core's `file.read` with `on`. It is removed when the app sees the program end in a terminal whose own process stayed the same (the person quit it), sees the terminal go, or a lookup replaces it. A reboot, `hc server stop`/start or a lost-and-restarted terminal (the terminal's process changes, and a reconnect forgets what was seen) keep it.
- Offer: for 60 s after the app starts or reconnects to the core, each listing checks for records whose terminal is live with a bare shell (no foreground, or a shell from the table) and a session no other record shares. ### Terminal font fallbacks

`feat/faint-and-fallbacks` (branched from `master`, fork only): `font_fallbacks` in settings.json (a list of family names, default empty) are the families terminal text takes a character from, in order, when its font lacks it, before the system's choice. - `HERDR:` change in `vendor/gpui-pre-macos/src/{open_type.rs,text_system.rs}`: the cascade asks each fallback family for the face's weight trait, read when the family loads. ### Focus history

`feat/focus-history` (branched from `master`, fork only): the app records where the person settles and shares it as the core document `herdr.focus`, and mods read it with `recentPlaces()`. A mod sees nothing while closed, so a go-to picker (the personal Fetch mod) only knew the moves made through itself; "Back to" and "Recent" need every focus move.

- A place is the model's focus: the active space's active tab's focused pane, with its terminal (null for a mod pane), tab, space, machine and arrival time. Every way focus moves ends in `publish`, which notes it (`note_focus`); overlays, popups, windows and layout terminal blocks (`focused_block`, `window_terminal`) never change the model's focus, so opening Fetch is no place and the place under it stays first.
- Debounce: a place counts once the person stays on it `SETTLE` (300 ms) (`focus_history::Settle`). It is noted when they move on or at the next tick (about 500 ms), stamped with when they arrived; quick hops (a pane passed through by keys) leave nothing, and coming back to the last noted place after a hop notes nothing new.
- Document: `herdr.focus` on this machine's core, `{"v":1,"places":[{pane, terminal, tab, space, machine, at}, ...]}`, newest first, at most 20, one place per pane; `pane` (non-empty string) and `at` (integer) are required; `terminal`, `tab`, `space` and `machine` may be null or absent (all `Option`; the app always sets `tab` and `space`). Places on another machine stay here with their `machine`; remote cores are never written. What the app doesn't read is written back as it was: other top-level fields (`Stored::rest`), other fields of a place (`Place::extra`), and entries without a `pane` or an integer `at` (`Stored::foreign`, the first 20 only so no client grows the document without limit, after the places, outside the merge and the cap). A `v` above 1 is read, never overwritten, and places noted against it are dropped rather than shown unshared. A value that isn't an object with an integer `v` and a `places` list is unreadable: warned once, and the next write replaces it with a fresh `{"v":1}`, since no client can use it and the version check still stops it overwriting a concurrent good write.
- Merge and conflicts: the union by pane, the later `at` winning, sorted by `at` then pane and cut to 20 (`merge`, order-independent, so writers converge). `sync` writes only when merging this window's unsent places keeps a visit the stored list lacks (`Stored::gains`), so another client's untidy list (unsorted, duplicates, over 20) isn't rewritten without a focus change; on `conflict` it reads, merges and retries (4 attempts), then leaves the places unsent. After a failed round the next waits 1 s, doubling per failure in a row up to 30 s, so a core that keeps refusing (a full disk, the size limit, endless conflicts) isn't asked every tick; success, a newly settled place, a `herdr.focus` doc event or a reconnect ends the wait. The window keeps the stored list plus what it noted and hasn't written (`History`), so another client clearing the list isn't undone. It writes at most one round at a time, from the existing 500 ms core tick (`flush_focus`), only while the core's event stream is up, and reads again on a `herdr.focus` doc event (`Pushed::focus`, which doesn't reread the layout documents) unless its version is the one this window wrote (`Pushed::focus_version`, `History::changed`), or on `missed`. A change seen while a round runs is read after it (`due` clears `stale` as a round starts; only a failure sets it). Each round's calls share one deadline (`OnCore`): 5 s, and 1 s for the last write on quit (`drain_documents`, skipped when nothing is unsent). Idle costs nothing: with nothing unsent and nothing changed `due` returns at once, and `publish` (every title change too) builds and compares the list only when a place settled (`note_focus`).

### Copy last output

`feat/copy-last-output` (branched from `master`, fork only): the pane right-click menu's copy group has "Copy last output" after Copy, only when the clicked terminal has a finished command's output its shell marked (OSC 133). It copies that output and toasts "Copied N lines".

- Where the output comes from: the app's own libghostty-vt view of the terminal (`Vt`), which already tracks OSC 133 per cell (prompt, input, output) and per row (prompt start). No herdr-core change and no per-chunk work: nothing runs until the menu opens or the command runs.
- Finding it (`Vt::last_output_selection`): on the primary screen only, from the newest prompt row up to the prompt above it. Scanning that block bottom-up, right to left, the first cell with text decides: output → `ghostty_terminal_select_output` there (Ghostty's own "output after the prompt above" selection, trailing blanks trimmed); input → the command printed nothing, `None`. A block with neither (Enter on an empty prompt, a right prompt and redraws included when the shell marks them as prompt) is skipped for the one above. Output without a marked prompt above it is not offered: Ghostty would select from the top of the history, which is wrong after the core's first paint (it carries no marks) and when the prompt scrolled out of the view's history.
- Text: `ghostty_terminal_selection_format_alloc` with that selection, plain, `unwrap` (wrapped lines joined) and `trim`, then trailing whitespace dropped.
- Menu: the window adds `last_output` (bool) to the menu `target` on a terminal's right-click and on `pane.menu`, as it does `selected`; the shipped menu shows the item from it (icon `file-text`).
- Command: `terminal.copy_last_output {terminal?}` (default: the focused terminal) reads the view the person sees (`shown_terminal_view`), else any other view of that terminal that has output. Each view (a pane, a peek) holds its own screen copy and one attached later lacks the marks written before it, while the menu reads the view right-clicked: falling back keeps the command from refusing what the menu offered. Without output it fails with a reason naming OSC 133, leaving the clipboard alone.
- Limits: the view's history (10,000 lines, 5 MiB) bounds how long an output can be; the first command after Herdr attaches to a terminal is not offered.
- Shell side: the shell must write the marks. The maintainer's zsh (chezmoi `dot_dotfiles/zsh/dot_zshrc`) gets them in Herdr panes by widening the tuios-only precmd/preexec block to `HC_TERMINAL_ID`; `defaults/AGENTS.md` carries a zsh and a bash snippet. The marks belong inside `PROMPT` (`A`…`B`) and `RPROMPT` (`P;k=r`…`B`): marks printed once from precmd leave a redrawn prompt (resize, `reset-prompt`) and a right prompt tagged as input, so Enter on an empty prompt would read as a command that printed nothing. A transient prompt is set inside the line editor where precmd never runs, so its `PS1` needs marking too: for oh-my-posh the zshrc wraps `_omp_get_prompt` so the `transient --eval` output ends with `_osc133_mark_prompt`, guarded on the function's current body (`[[ $functions[_omp_get_prompt] != *_osc133_omp_get_prompt* ]]`) so a re-sourced `.zshrc`, which re-runs `oh-my-posh init`, wraps the fresh definition and never the wrapper itself; Starship's transient prompt plugins need the same. Herdr can't recover an unmarked redraw itself: an all-input prompt row reads the same whether Enter was pressed on it empty or `cd` was typed there (`vt::tests::last_output_needs_marks_on_the_primary_screen` pins this). A half-typed line left with Ctrl+C is input and reads that way regardless. Verified live in an isolated instance with the real oh-my-posh config: without the wrapper the item went away after two empty Enters; with it, the previous output stayed copyable.
- Tests: `vt::tests::{last_output_is_the_last_finished_command_between_its_prompts, last_output_reaches_into_scrollback_and_joins_wrapped_lines, last_output_needs_marks_on_the_primary_screen}`, `window::tests::pane_menu_copy_items_act_on_the_clicked_terminal` (target `last_output`, the copy and its toast, failure on an unmarked terminal and on the alternate screen), `mods::render_tests::pane_menu_copy_items` (visibility and order).

### Shared git status and selective mod redraws

`perf/events` (branched from `master`, fork only): mods get one cached git status per folder, and a change redraws only the mod copies that read it. Pane header info's `{branch}`, `{ahead}`, `{behind}` and `{dirty}` read this status.

- Git status: `gitStatus(folder, { on, files })` (branch, head, upstream, ahead and behind, change counts, each file with `files`), shared by every copy and window. A local repo is looked at again only when something in it changes on disk (one watcher; ignored folders, objects, logs and lock files don't count), once a burst settles (`QUIET`, 300 ms) and at most once a second (`MIN_GAP`, or 4 times as long as git took). One look answers every folder asked about in a work tree. Another machine's folder has no watcher: `refreshGitStatus` asks again, and an answer read after a minute (`STALE`) is asked again. `nextGitStatus` serves work outside render. The app's own folder tracking (space names, pane branches) reads the same answers rather than running git itself.
- Selective redraws: `shared()` reads are recorded per key, like snapshot reads, so `setShared` redraws only the copies that read that key. Refreshes skip copies not on screen; a copy coming into view catches up on what it missed.
- Title spins: a terminal listing that changes only an agent's spinning title (stripped before publishing) is an ordinary tick, not a publish.
- Why: Agent Deck's spaces panel ran three git processes per place after every agent status change, and the app ran `git rev-parse` per terminal at each turn's end (about 11% CPU in child processes during a status storm); every `setShared` redrew every loaded copy, hidden ones included.
- Tests: `git_status::tests::{detached_initial_and_linked_worktrees, mods_get_the_file_list_only_when_they_ask, events_in_ignored_folders_objects_and_locks_do_not_count, a_burst_of_events_is_one_look_after_it_settles_and_looks_are_spaced, a_watched_repo_is_looked_at_again_when_it_changes_and_not_for_ignored_churn, a_new_ignored_folder_does_not_count_whatever_its_first_event, a_folder_outside_any_repo_is_false, reads_share_one_look_and_answers_redraw_only_on_change}`, `mods::tests::{a_shared_value_redraws_only_the_copies_that_read_it, a_copy_coming_into_view_is_told_and_catches_up_on_missed_refreshes}`, `window::tests::folder_info_comes_from_the_git_status`.

### Name-matched icons

`feat/name-icons` (branched from `master`, fork only): spaces and panes get an icon that matches their name, with nothing to pick and nothing stored.

- Default: `space_avatar` unset (or unknown) is `glyph`, a Nerd Font icon tinted like the rest of the chrome; mods read `settings().space_avatar` as `"glyph"` then, never null. `emoji` stays selectable; `letter` and `repo` draw as they did, except that repo's glyph for a folder with no known project is the name-matched one.
- Panes: unchanged mechanism (see Tab and pane icons). A bare shell showing its automatic name gets its noun's icon from `defaults/pane-icons.json`, which `pane_icons::tests` checks covers every noun of `pane-names.json` (every automatic name ends in one, so there is no adjective or id-hash fallback). With glyph as the default, that now applies without setting `space_avatar`.
- Spaces: the spaces mod matches a space's name word by word (lower case, split at punctuation and camelCase, a trailing s also tried): first a curated word anywhere in the name, then a word that is a glyph's own name (Material Design, then Font Awesome, Codicons, Octicons and the other icon sets; not Powerline or Pomicons) or an emoji's own name or keyword (no faces, people or flags; the shortest name wins). A name matching nothing takes one of the 60 suggested glyphs or emoji from FNV-1a of the name, stepping past any icon another space shows; such collisions are settled by (hash, name, id), never by the order the list shows, so a reorder swaps no icons. A space's own choice (Change icon…) wins until Clear icon.
- Data, not code: `defaults/mods/icon-picker/names/keywords.json`. `icons: [{words, glyph, emoji}]` holds about 70 entries of common project words (docs, api, infra, notes, deploy, k8s, finance…), each word once, glyphs by their `glyphs.json` name, emoji as `emoji.json` writes them, none a person, a flag or a status (the robot and speech balloon are the only Smileys). `glyph_sets` and `no_emoji_groups` say how the rest is matched, and `deny: {words, emoji}` keeps anything that reads as an agent's state (check, alert, loading, done, a warning sign, an hourglass) from matching beside Herdr's status marks. Herdr ships it beside the picker's name lists so any mod can read it; nothing in Rust reads it.
- Why not Rust: the three questions from upstream's AGENTS.md all answer no. The app doesn't act on a space's icon, mods see the name, and a mod can match it correctly. The only Rust change is the default value.
- Perf: the name files are read once, the first time a glyph or emoji avatar is drawn (off the UI thread, as icon search does), and each name's match is cached, so a render costs a map lookup per space. Until the files are read, automatic tiles are blank in their colour.

### Pane header info

`feat/header-info` (branched from `master`, fork only): `pane_header_info` in settings.json is a template of extra words an agent pane's header shows between its name and its status, as room allows. Off by default: unset or blank, panes publish `header_info: null` and every shipped mod draws byte for byte as without it.

- Grammar (`src/header_info.rs`): `{ask}`, `{state}`, `{elapsed}`, `{branch}`, `{ahead}`, `{behind}`, `{dirty}` are keys; other text, an unknown `{word}` too, is literal. `·` or `|` split segments; the separator is drawn as written, with its spaces, between two segments that show. Widths are estimated at 0.6 em a character, wide characters (Chinese, Japanese and Korean (CJK), emoji) twice: `fit` and the headers' estimate of the name beside it share `header_info::width` (`headerTextWidth`). ### Rejected text experiments

Two text-quality experiments measured against the shipped thicken, contrast and weight settings, and not kept. The numbers are here so neither is tried again without a new reason.

- **Gamma-correct (linear-light) glyph blending.** A Skia-style preblend (`SkMaskGamma`): a per-sprite gamma in `MonochromeSprite`, the shader assuming the text's perceptual inverse as background. Headless Metal readback, JetBrains Mono 12 px: at gamma 2.2 plain light-on-dark ink went from 1.21× dark-on-light to 1.91×; with thicken 30 and contrast 0.2 (equal ink in both polarities, 1.00) it split to 1.61× and moved light-on-dark ink +23% away from the Ghostty match. Equal polarities needed gamma ≈ 0.6, the opposite of linear light. The polarity gap in Herdr comes from CoreGraphics dilating light text more (`glyph_dilation_for_color`), not from gamma-space blending, and thicken already removes it by giving both polarities one mask. Prototype commit `f7a2a85` (branch deleted).
- **Subpixel (LCD) smoothing on macOS.** CoreGraphics produces no per-channel coverage on macOS 27 with any public or private smoothing setting tried (`setShouldSmoothFonts`, `AppleFontSmoothing`, `CGContextSetFontSmoothingStyle`), so it would need swash rasterising 3× horizontally plus FreeType's 5-tap filter, with CoreText keeping shaping and advances (they match to 0.00000 px). About half the plumbing exists from Zed's Windows/Linux work (`TextRenderingMode`, `SubpixelSprite`); Metal lacks the subpixel atlas kind, shader and batch. Estimated 5–8 days and ~1,000 fork-only lines. Not built at first (since built, see "Subpixel smoothing" above): swash can't reproduce CoreGraphics' smoothing dilation, so it drops the Ghostty match thicken was tuned for, it puts colour fringes into screenshots and screen shares, and side-by-side 1x renders showed fringing without a clear sharpness gain.
